# CLAUDE.md — `constellation.sequencing`

This file extends the project-wide rules in [../../CLAUDE.md](../../CLAUDE.md). Read that first.

`sequencing/` absorbs **NanoporeAnalysis** as a clean rewrite. The lab's workflows span genomic DNA (POD5 → Dorado → HiFiASM → polish → scaffold → annotate), transcriptomic cDNA (segmented edlib demux → ORF prediction → kmer-cluster consensus → predicted proteins feeding `massspec` libraries), and direct-RNA / modifications. Rather than mirroring `massspec`'s theoretical/empirical/scoring trio, sequencing's natural shape is `acquisitions + samples + reads + alignments + (genome reference, annotation, transcript reference) + assembly + quant + annotation tools + genetic_tools` — see the conventions section below for the rationale.

## Module index

**S1 transcriptomics demux pipeline shipped:** `constellation transcriptome demultiplex --reads ... --library-design cdna_wilburn_v1 --samples ... [--min-aa-length 60] [--threads N] [--batch-size 100000] [--resume] [--progress] [--emit-fastq]` runs SAM/BAM → READ_TABLE → READ_SEGMENT_TABLE / READ_DEMUX_TABLE / ORF_TABLE → Protein × Sample count matrix. The `--samples` TSV format is **header-required**, columns `sample_name + barcode_id` (plus optional `file` for multi-file mode, `description`); `sample_id` is auto-assigned per unique `sample_name` so rows sharing a `sample_name` aggregate into one sample with multiple `(acquisition, barcode)` edges — that's how multi-barcode multiplexing and multi-flowcell aggregation are expressed. The resolved `Samples` container is persisted under `<output-dir>/samples/` (ParquetDir bundle: `samples.parquet` + `edges.parquet` + `manifest.json`) so downstream stages (`transcriptome align`, `transcriptome cluster`) load it back via `load_samples(...)` and **do not require `--samples` to be re-supplied**. Stages: `_plan_chunks` (parent-only chunk-spec computation: BAM record-boundary virtual offsets via fast no-decode pysam scan, SAM newline-aligned byte ranges) → `run_fused_demux_stage` (N parallel workers each open their own pysam handle on a slice of the source file, do ingest + `locate_segments` + `predict_orfs` + `resolve_demux` (sample_id resolved locally via the Samples container) + `build_partial_quant` end-to-end, write 5 shards: reads / read_segments / read_demux / orfs / feature_quant; multi-file inputs allowed — `--reads file1.bam file2.bam` or `--reads dir/` with a 'file' column in the samples TSV mapping each (sample, barcode) edge to its source acquisition) → `resolve` (streaming aggregator: `aggregate_partial_quants` opens `feature_quant/` as a `pa.dataset` and group_by-sums into the final small matrix; emits `feature_quant.parquet` + `proteins.fasta` + `protein_counts.tsv`). No single-file `read_demux.parquet` aggregation — `read_demux/` stays a partitioned dataset queryable via `pa.dataset.dataset(read_demux/)`. Per-worker file slicing eliminates the parent-serial ingest bottleneck — at `--threads 96` on a cluster node, the BAM is decoded 96 ways in parallel. Optional `--emit-fastq` adds a fourth stage (`transcriptome/fastq.py::emit_per_sample_fastq`) that streams `read_demux/` ⨝ `reads/` (transcript-trimmed window, strict Complete-only filter — same predicate as `_iter_demux_read_batches(only_complete=True)`) and routes each batch to per-sample `gzip.open` handles, emitting `fastq/<sample_name>.fq.gz` (aggregated across acquisitions/barcodes that share `sample_id`); atomic `.tmp → .fq.gz` rename + own `fastq/_SUCCESS` marker make it resume-safe and a clean bolt-on for users re-running the same command with `--emit-fastq --resume` on an existing output-dir.

`HardThresholdScorer` matches NanoporeAnalysis `_fixed1` semantics with three deliberate accuracy improvements over the upstream baseline (filter edlib `-1` no-match sentinel; short-circuit on empty subjects; skip the literal-string `cDNA[1] == 'Unknown'` check that hides real annotations behind `'Unknown Fragment'`). Parity vs lab `_fixed1` baseline: 99.5% per-read status agreement, 99.78% barcode agreement, **100% count-matrix per-cell parity, 100% protein-FASTA sequence-set match**.

Other shipped: `Acquisitions` / `Samples` containers (validators-only mode), `cdna_wilburn_v1` design (24 barcodes, regenerable via `scripts/build-sequencing-primers-json.py`), `align/{locate,pairwise}` (edlib-backed `locate_substring` + `pairwise_align`), `Scorer` Protocol seam (`HardThresholdScorer` shipped is the production scorer; `ProbabilisticScorer` deferred indefinitely — see scoring-domain rule below), `transcriptome.simulator` (synthetic-read corpus generator: `ReadSpec` + `generate_stress_test_specs` + `simulate_panel` writes SAM + ground-truth parquet for stress-testing the scorer + as a regression fixture for cross-Dorado-version drift), `scripts/analyze-demux-statistics.py` (dataset-level filter + Arrow join + numpy histograms; per-status edit-distance + polyA-length distributions; **diagnostic tool**, not a calibration target — used for spotting basecaller drift across Dorado versions, characterising per-barcode systematics, regression-testing scorer changes).

19 self-registering Arrow schemas including `READ_TABLE` extended with `dorado_quality` (qs:f), `read_group` (RG:Z), `duplex_class` (dx:i, int8 — 0=simplex/1=duplex/-1=simplex-with-duplex-offspring) so the Dorado tags useful for QC + S3 duplex-artifact validation are captured at S1 ingest; `READ_DEMUX_TABLE` extended in S1 with `status` (string), `is_fragment` (bool), `artifact` (string, populated `"none"` until S3); `READ_SEGMENT_TABLE.score_delta` (nullable int32; best-vs-second-best gap on barcode rows).

**Reference layer shipped (S1 reference data classes):** the `Reference` stub split into three sibling Library-shaped containers — `GenomeReference` (`CONTIG_TABLE` + `SEQUENCE_TABLE`), `Annotation` (`FEATURE_TABLE`, FK closure into a `GenomeReference` via `validate_against`), `TranscriptReference` (`TRANSCRIPT_TABLE`; `from_annotation(genome, annotation)` materialises spliced transcripts via strand-aware exon concatenation against contig sequences). Each ships PK/FK closure on construction + ParquetDir Reader/Writer Protocols. `GeneticTools` is the cRAP-equivalent for genomics — 67 curated entries across 9 categories at `constellation/data/genetic_tools.json`, regenerable via `scripts/build-genetic-tools-json.py`; `load_default_genetic_tools()` is the bundle loader. Hand-rolled stdlib-only readers: `readers/fastx.py::read_fasta_genome` / `read_fasta_transcriptome` / `read_fasta_genetic_tools`, `readers/gff.py::read_gff3` / `write_gff3` (two-pass parent resolution, gzip-aware, multi-parent expansion, `##FASTA` boundary), `readers/bed.py::read_bed`. `FEATURE_QUANT` extended with a `feature_origin` column (vocabulary `'gene_id'` | `'transcript_id'` | `'cluster_id'` | `'genetic_tool'` | `'protein_uniref'` | `'protein_hash'`); `transcriptome.quant.to_feature_quant` projects the existing naive-ORF output into the canonical schema under `feature_origin='protein_hash'`. CLI wired: `constellation reference {import, fetch, search, list, where, link, default, remove, summary, validate}`; `fetch` uses stdlib `urllib.request` against Ensembl / Ensembl Genomes / RefSeq URL conventions (no NCBI Datasets CLI dep); `remove` deletes a cached `(organism, release)` and auto-retargets `defaults.toml` + `current` to the most-recently-fetched survivor when the removed entry was the default/current, mirroring the auto-default-on-first-fetch behaviour so an organism with ≥1 install always has both pointers populated. `Assembly.to_reference` renamed to `to_genome_reference`; companion Annotations build from downstream BUSCO / repeat / telomere passes (still stubbed).

**Mode A genome-guided gene counting shipped (S2):** `constellation transcriptome align --demux-dir <s1-out> --reference <handle> --output-dir <dir> [filter knobs] [--resume] [--progress]` chains directly off the S1 demux output — reads input BAM paths from the typed demux manifest (`transcriptome.manifest.read_manifest_dir`) and loads the resolved `Samples` container from `<demux-dir>/samples/` via `load_samples`; **`--samples` is not a flag on align** (the user supplies it once at demux time, and the persisted ParquetDir bundle rides forward through every downstream stage). `--reference` accepts a reference cache handle (e.g. `homo_sapiens@ensembl-111`); for an off-cache ad-hoc reference root, pass `--reference-dir <PATH>` instead (escape hatch — manifests written this way omit `reference_handle` and can't be opened in the genome browser dashboard until the reference is imported via `constellation reference import`). The output manifest (`manifest.json`) is schema v3: top-level `reference_handle`, `reference_path`, `assembly_accession`, plus `outputs` for downstream consumers (cluster propagates these forward, the viz layer matches sources to references via the handle). Demux now also emits a typed v3 manifest (`kind="demux"`), so the three stages share one `read_manifest_dir` / dataclass-dispatch contract. Three stages: (1) `align` — `map_to_genome` materialises a cached genome FASTA + `.mmi` index from the `GenomeReference`, runs minimap2 splice-aware (`-ax splice -uf --cs=long --secondary=no`) per input file, then `samtools cat | samtools sort | samtools index` into one coordinate-sorted `bam/aligned.bam`. (2) `decode_filter_overlap` — `_bam_alignment_chunks` plans virtual-offset chunks; the fused worker (`fused_decode_filter_overlap_worker`) decodes each chunk via `read_bam_alignments_chunk`, applies `apply_filter_predicates` (length / aligned-fraction / mapq / primary-only — vectorised pa.compute), then `compute_gene_overlap` (sort+searchsorted sweep-join against the broadcast gene set, best-overlap selection, antisense gating). Each worker writes 4 partitioned shards: `alignments/`, `alignment_tags/`, `gene_assignments/`, `stats/`. Worker-local alignment_id packed as `(worker_idx << 32) | local_idx` for collision-free partition concatenation. (3) `count` — `count_reads_per_gene` materialises `gene_assignments/` + `read_demux/` as pa.Tables (bounded ~3 GB / ~10 GB at 200M-read scale), hash-joins on `read_id`, group_by-sums to `FEATURE_QUANT(feature_origin='gene_id')`, and populates `tpm` per-sample as `count × 1e6 / sum_in_sample(count)` — long-read TPM convention (one read = one transcript, no length normalisation). The CLI then writes wide gene × sample TSVs alongside the canonical parquet via `quant.gene_matrix.build_gene_matrix` + `render_gene_matrix_tsv`: `gene_counts.tsv` and `gene_tpm.tsv` (controlled by `--matrix-format {count,tpm,both,none}` default `both`, with `--matrix-min-count N` to drop low-total rows; gene rows carry feature_id / gene_name / gene_biotype / contig / start / end / strand / length annotation columns + one float column per sample, with zero-fill for genes absent from `feature_quant` for stable cross-run indexing). Single output entry point (`pa.Table` inputs) serves both pipeline (CLI materialises from datasets) and tests/Jupyter (callers pass small in-memory tables).

**Streaming pipeline rule:** the in-memory `Alignments` container + `Alignments.filter` (with per-stage `metadata_extras['filter_steps']` audit) + `count_reads_per_gene` API are for tests + Jupyter only — at 30–200M alignments per real run (Pichia ~30M, mouse/Arabidopsis ~200M), the pipeline never materialises a full Alignments. The fused-worker streaming + bounded-resolve-stage memory pattern is the only production path. The same rule extends to **every resolve-stage aggregator** — `build_pileup`, `aggregate_junctions`, `assign_blocks_to_exons`, `compute_exon_psi`, and `cluster_by_fingerprint` — all of which use **Arrow joins / group_by / sort_by for the cardinality-bounded shape operations + PyTorch CPU tensors for the per-partition numerical kernels** (sweep-line RLE, searchsorted interval-overlap, scatter-add deltas, boundary scans). `to_pylist()` followed by Python row loops over alignment-block-cardinality data is **forbidden** on the resolve-stage hot path — it pinned ~12+ hours on a single thread at mouse scale in the pre-refactor code, with hundreds of GB of Python-object growth. `build_pileup` and `assign_blocks_to_exons` take an optional `output_path` arg; when provided they're **streaming Parquet writers** that emit per-partition / per-batch `pa.RecordBatch`es directly to disk without ever holding the aggregate in RAM (`compute_exon_psi` accepts the resulting path back as a `pa.dataset` to extract distinct `(alignment_id, data_exon_id)` pairs in batches). **CLI namespace rule:** gene-counting is a transcriptomics analysis (consumes a reference; not a reference-management op), so it lives at `transcriptome align`, not `reference align`. Mode B (de novo clustering) shares the same verb when it lands — dispatch on `--reference` / `--reference-dir` presence; both absent → "not yet implemented" with exit 2. **Two-layer minimap2 split:** `align/minimap2.py::minimap2_run(target, queries, *, output_path, args, threads)` is the generic, use-case-agnostic subprocess wrapper (knows nothing about splice / preset); `align/map.py::map_to_genome` is the use-case orchestrator that hard-codes the splice flags. Future `map_assembly` / `map_dna_to_genome` / PAF-output verbs all compose `minimap2_run` directly with their own arg lists — no subclassing or wrapping. mappy is rejected (user-confirmed slower); the `map_reads` two-backend stub is deleted. **Memory budget for the resolve stage:** `gene_assignments` ~3 GB + `read_demux` ~10 GB at 200M reads — fits comfortably on workstation RAM. The bigger derived outputs (`alignment_blocks/` ~25 GB, `alignments/` ~30 GB, `block_exon_assignments` ~50 GB on disk at 1.6B-row mouse scale) are now bounded in RAM by the streaming-Parquet handoff between `build_pileup` → `build_derived_annotation` → `compute_exon_psi`. If we cross 1B reads, `count_reads_per_gene` lifts into an Arrow-Dataset-streaming variant — single-function refactor at that point, not a new public API.

**Phase 1 alignment-derived intermediates — now default-on (was opt-in via `--emit-*`):** three core schemas in `schemas/alignment.py` — `ALIGNMENT_BLOCK_TABLE` (one row per CIGAR-derived M/=/X-contiguous block; cs:long-derived `n_match`/`n_mismatch` populated when minimap2 emitted `--cs=long`, null when only CIGAR is available; contig comes via the `alignment_id` FK to `ALIGNMENT_TABLE.ref_name` to save a column × ~600M rows at PromethION scale), `INTRON_TABLE` (single denormalised intron view: one row per *observed* `(contig_id, donor_pos, acceptor_pos, strand)` tuple, augmented with `intron_id` cluster ID + `is_intron_seed` bool — multiple rows can share an `intron_id`; replaces the retired `SPLICE_JUNCTION_TABLE`), `READ_FINGERPRINT_TABLE` (per-read splicing-topology hash via `xxhash.xxh64` over the canonical byte layout `contig_id (int64 LE) || strand (utf-8) || n_introns (uint32 LE) || intron_id_1 (int64 LE) || ...`; primary alignments only; the Phase 2 cluster key — donor/acceptor positions don't enter the hash directly, just the intron_ids assigned by `cluster_junctions`). Producers: `align/cigar.py::parse_cigar_blocks` + `parse_cs_long_blocks` (state-machine parsers; block-break rule is N + D≥`intron_min_bp` but never long I); `quant/genome_count.py::extract_alignment_blocks` (worker-layer orchestrator); `quant/coverage.py::build_pileup` (sweep-line RLE pile-up via per-partition torch `unique` + `scatter_add_` + `cumsum`; per-sample stratification via `read_to_sample: pa.Table` Arrow-join with a `sample_id=-1` sentinel when None; streaming Parquet writer when called with `output_path`); `quant/junctions.py::aggregate_junctions` + `cluster_junctions` (Arrow `sort_by([alignment_id, block_index])` on a NUMERIC-only block projection — strings stay out of the heavy sort + combine_chunks; torch diff on consecutive `alignment_id` to find junction rows; `group_by([contig, donor, acceptor, strand]).count(alignment_id)` after attaching strand/ref_name via two final small joins. `count(alignment_id)` matches `count_distinct(read_id)` since `alignment_id` is 1:1 with `read_id` on primary alignments and a plain `count` is much cheaper than `count_distinct`. Motif lookup prefetches each contig's sequence ONCE into a per-call dict — `GenomeReference.sequence_of` is uncached and decodes the full chromosome string per call, so per-junction calls degenerate catastrophically past ~10K unique junctions); `transcriptome/fingerprints.py::compute_read_fingerprints`. CLI flags on `transcriptome align`: `--no-cluster-junctions` (opt-out for diagnostic raw-only output), `--intron-tolerance-bp INT` (default 5), `--intron-motif-priority STR,STR,...` (default `GT-AG,GC-AG,AT-AC`), `--no-coverage`, `--no-derived-annotation`, `--min-exon-depth INT` (default 5), `--min-intron-read-count INT` (default 3), `--emit-cs-tags` (still opt-in), `--intron-min-bp` (default 25). Wired through the existing fused worker (`emit_blocks=True` always-on) + resolve-stage aggregators that materialise `alignment_blocks/` + `alignments/` once and emit `introns.parquet` / `coverage.parquet` / `derived_annotation/` / `block_exon_assignments.parquet` / `exon_psi.parquet`.

**Part A — greedy support-ranked intron clustering:** `quant/junctions.py::cluster_junctions(introns, *, tolerance_bp=5, motif_priority=("GT-AG", "GC-AG", "AT-AC")) -> pa.Table` replaces the uniform-quantum `(d // q) * q` fingerprint quantisation. Algorithm: per `(contig_id, strand)` partition, sort raw junctions by `(read_count desc, motif_rank asc, contig asc, donor asc, acceptor asc)`; for each junction, bisect-search per-partition seed list for any seed within ±W on BOTH donor AND acceptor (L∞ ball, not L₂); absorb if found, else become a new seed. Output is a single `INTRON_TABLE`-shaped table — same row count as input, with `intron_id` + `is_intron_seed` re-assigned. The window concept is fully absorbed at clustering time; fingerprint hashing then snaps per-read junctions to canonical `intron_id` via hash-join. **Breaking API change:** `compute_read_fingerprints(alignment_blocks, alignments, contigs, introns)` requires the introns table now and ignores the legacy `intron_quantum_bp`. The CLI flag rename is `--intron-quantum-bp` → `--intron-tolerance-bp` on both `transcriptome align` and `transcriptome cluster`. The cluster command's tolerance default is "read from align manifest"; supplying `--intron-tolerance-bp INT` re-runs `cluster_junctions` against the raw per-position rows in `introns.parquet` before fingerprinting, so users can sweep tolerance without re-running align.

**Why support-ranked clustering vs uniform quantisation:** uniform `(d // q) * q` bin edges are arbitrary — a dominant donor at position 1239 hashes into bin 1230 while a stray cryptic at 1240 hashes into bin 1240, splitting reads that biology says agree. The right physical model is asymmetric — one dominant `(donor, acceptor)` per intron with a long tail of low-support cryptics, all anchored to the same GT-AG dinucleotide pair. Support-ranked clustering picks the highest-support junction as the cluster seed (with GT-AG > GC-AG > AT-AC > non-canonical motif tiebreak) and absorbs neighbours within tolerance. The user-facing tolerance is now an explicit `±bp` window, not an implicit binning grid.

**Part B — derived annotation + exon discovery (default-on):** `quant/derived_annotation.py::build_derived_annotation(coverage: pa.Table | Path, introns, alignment_blocks, alignments, contigs, *, read_to_sample: pa.Table | None = None, block_assignments_output_path: Path | None = None, min_exon_depth=5, min_intron_read_count=3) -> (Annotation, BLOCK_EXON_ASSIGNMENT_TABLE | Path, EXON_PSI_TABLE)` derives a data-informed annotation from the always-on Phase 1 substrates. When `block_assignments_output_path` is set, the M:N edge table streams to that Parquet file and `compute_exon_psi` reads it back as a `pa.dataset` to extract distinct `(alignment_id, data_exon_id)` overlap pairs in batches — the table never materialises in RAM. Pipeline: (1) `derive_exons` filters introns to clusters where `group_by(intron_id).sum(read_count) >= min_intron_read_count` (filter on cluster total, not per-row); coalesces RLE coverage above `min_exon_depth`; per `(contig, strand)`, segments each covered interval at trusted intron donor + acceptor positions via `bisect`-slice against a sorted-once-per-partition cut list (an `O(log N + K)` lookup per interval, **not** the `p for p in cuts_set if iv_start < p < iv_end` set-comprehension that pre-refactor pinned a single thread for hours at ~80K cuts × tens of thousands of intervals × 50 partitions); drops pieces whose `(start, end)` exactly matches a trusted intron's span (these are introns, not exons) — keeps the rest as minimal exon segments. (2) `roll_up_genes` builds an exon graph (edge iff a trusted intron seed has `donor==exon_a.end` AND `acceptor==exon_b.start` on the same `(contig, strand)`); connected components via `core.graph.network.Network` are derived genes; each exon's `parent_id` rewrites to its gene's `feature_id`. Output writes to `FEATURE_TABLE` with `source='constellation_derived'`. (3) `assign_blocks_to_exons` produces a long-form M:N edge table `BLOCK_EXON_ASSIGNMENT_TABLE` keyed on `(alignment_id, block_index, data_exon_id)` — most rows 1-to-1 (a clean spliced block falls inside one exon), but boundary-jitter / intron-retention reads emit 2+ rows per block. Per-contig vectorised torch `searchsorted` + `repeat_interleave` expansion with **two-sided bounds** — `hi = searchsorted(exon_starts_sorted, block_end)` for `exon_start < block_end`, AND `lo = searchsorted(cummax(exon_ends_sorted), block_start)` (the monotonic prefix-max of `exon_end` in start-sorted order) for "could this exon possibly still be active at block_start". The lower bound is load-bearing: with `lo=0` the candidate range degenerates to ~all exons per block at scattered-exon scale and explodes intermediate memory by ~10,000×. Adaptive batch size caps peak intermediate at ~250M int64s regardless of `n_exons`. (4) `compute_exon_psi` produces `EXON_PSI_TABLE` with per-(exon, sample) inclusion / exclusion / PSI substrate where `PSI = n_inclusion / (n_inclusion + n_exclusion)` (FLAIR / IsoQuant convention; gene-spanning alignment with any block overlap → inclusion, gene-spanning with no overlap → exclusion). Gene-spanning classification uses per-contig torch chunked broadcasting (auto-tuned ~1 GB intermediate per chunk) to enumerate `(alignment, gene)` overlap pairs. `role_id` is emitted as int8 (0=spanning, 1=partial) directly from `_classify_alignments_per_gene` — not a `"spanning"` / `"partial"` string column — because at PromethION scale the 419M-row aln_exon_role cross-join carries it forward and string vs int8 is a ~4 GB peak difference. The left-join + indicator + group_by chain runs in **streaming chunks via `_join_aggregate_streaming`** (~50M-row chunks; zero-copy `Table.slice`) with per-chunk partial group_by sums merged in a final pass — materialising the full 419M-row left-join would otherwise add ~20 GB transient. Three new schemas: `BLOCK_EXON_ASSIGNMENT_TABLE` in `schemas/alignment.py`, `EXON_PSI_TABLE` in `schemas/quant.py`, plus the `derived_annotation/` ParquetDir bundle (drop-in for `Annotation`'s `ParquetDirReader/Writer`). Opt-outs: `--no-derived-annotation` skips Part B entirely; `--no-coverage` suppresses `coverage.parquet` from final outputs (`build_pileup` still writes it as a transient that `build_derived_annotation` reads back; the CLI unlinks the file after the derived-annotation pass when `--no-coverage` is set). v1 limitations: pure single-exon genes (no introns) are not discovered; coverage stratification is unstranded (per-strand exon derivation uses unstranded coverage as a depth-thresholding substrate); differential exon-abundance estimation (negbin LRT across samples) is deferred — `EXON_PSI_TABLE` is the v2 substrate.

**Phase 2 genome-guided fingerprint clustering shipped:** `constellation transcriptome cluster --mode genome-guided --align-dir <s2-out> --demux-dir <s1-out> --output-dir <dir> [--build-consensus] [--max-5p-drift 25] [--max-3p-drift 75] [--intron-tolerance-bp INT] [--min-cluster-size 1] [--per-sample-clusters] [--write-fasta] [--write-summary] [--threads N] [--resume] [--progress]` ships an isoform-resolution clusterer that consumes the always-on `alignment_blocks/` + `introns.parquet` from align. `Samples` loads from `<demux-dir>/samples/` (no `--samples` flag); the align manifest is read via the typed `read_manifest_dir`. Algorithm: (1) load `introns.parquet`; if `--intron-tolerance-bp` differs from the align manifest's value, re-run `cluster_junctions` against the raw per-position rows in-place (sweeping tolerance never requires re-running align); (2) re-derive fingerprints via `compute_read_fingerprints(alignment_blocks, alignments, contigs, introns)` — Arrow-native pipeline: sort blocks by `(alignment_id, block_index)` numeric-only, derive per-read junctions via numpy shift (`donor = ends[:-1], acceptor = starts[1:]` masked by same-alignment), hash-join junctions ⨝ introns for intron_id substitution, group-by alignment_id, then a `xxh64` loop bounded by N_alignments (~3 min @ 200M reads vs blake2b's ~33 min, with zero `to_pylist` on block cardinality); (3) `cluster_by_fingerprint` resolves per-fingerprint row indices into each source table once via `pc.index_in` (reads, primary_lookup, metrics), sorts a narrow all-numeric keys table `(row_idx, contig_id, strand, sample_id, fingerprint_hash, reads_idx, primary_idx, metrics_idx?)`, walks cluster boundaries on the narrow sort, and `pc.take`s per-cluster from each source — the wide `enriched` table that previously dragged `sequence` (~50 GB at PromethION scale) through the global sort and crashed with `ArrowInvalid: offset overflow while concatenating arrays` is gone; (4) strand-aware 5'/3' span-coherence drift filter — on `+`, 5' = `span_start`; on `-`, 5' = `span_end`; singletons skip the filter; (5) Layer-0 dereplicate trimmed transcript-window sequences (blake2b-8 hash of `READ_TABLE.sequence[transcript_start:transcript_end]`) per cluster and pick the most-abundant unique sequence's read as representative (tiebreak by mean `dorado_quality`); (6) optional `--build-consensus` per-position weighted-PWM majority vote on the genome coordinate frame via the shared `align/consensus.py` kernel — `alignment_cs` accepts either `pa.Table` (eager, for tests + small Jupyter) or `pa.dataset.Dataset` (the CLI default; per-cluster filter pushdown materialises only the ~tens of cs:long rows for the current cluster, sidestepping the ~50 GB eager load). **Mega-cluster streaming refactor:** `_emit_cluster` now operates entirely on Arrow columns + numpy without ever calling `slice_table.to_pylist()` — drift filter is vectorized numpy on `span_start`/`span_end`, Layer-0 derep is `pa.Table.group_by("sequence").aggregate(...)` (collapsing 2.15M-row mega-clusters to ~100K-500K unique-sequence groups in C++-speed), membership rows are built via `pa.Table.from_arrays(...)` with `pc.if_else` for the per-row role/metric branches, and `_emit_cluster` returns `(cluster_row_dict, membership_table: pa.Table)` so the per-cluster loop accumulates a `list[pa.Table]` and `pa.concat_tables(...)` at the end (zero-copy when schemas match) instead of materialising tens of GB of Python dicts. `build_consensus` adds `threads: int = 1` + `scatter_chunk_size: int = 100_000` kwargs: per-member `_cs_votes` parsing dispatches across a `ThreadPoolExecutor` (regex releases the GIL) and per-chunk results accumulate into ONE batched `flat_pwm.index_add_(...)` per ~100K members instead of one scatter call per member. CLI `--threads N` forwards to `consensus_threads` through `cluster_by_fingerprint` so the mega-cluster consensus drops from ~30-60 min sequential to ~2-5 min with 16 threads. **Granularity contract for `transcriptome cluster --mode genome-guided`:** clustering is **per-isoform**, not per-gene. The `fingerprint_hash` now keys on `(contig_id, strand, [intron_id_1, intron_id_2, ...])` (no donor/acceptor positions enter the hash directly — the intron_id is the canonical cluster identifier assigned by `cluster_junctions`). Different splicing topologies on the same gene fall into different clusters; reads agreeing on canonical-intron-id splicing collapse into one cluster regardless of substitution noise (within-cluster heterogeneity surfaces via `n_unique_sequences > 1` and per-membership `match_rate` < 1.0). A gene with N annotated isoforms produces ≥ N clusters in v1; the inequality picks up novel isoforms (correctly distinct), truncated reads that miss an internal junction (incorrectly split; deferred subset-junction merge is the v2 fix), and basecaller-induced junction-call errors (rare; surfaces as singletons). Alt-TSS / alt-polyA isoforms whose intron chain is identical fall into the *same* fingerprint cluster initially and the drift filter separates the long-tail divergent reads.

**Phase 3 de novo first-round assembly shipped (`cluster/denovo/` subpackage):** `constellation transcriptome cluster --mode de-novo --demux-dir <s1-out> --output-dir <dir> [--identity 0.98] [--max-5p-overhang 30] [--max-3p-overhang 30] [--kmer 15] [--window 10] [--minimizers-per-seq 50] [--min-cluster-size 1] [--min-abundance 1] [--max-cluster-rounds 1] [--error-model {default,empirical}] [--overdispersion 0.0] [--[no-]fold-insertions] [--consensus-max-passes 3] [--[no-]predict-orfs] [--min-aa-length 60] [--emit-cluster-detail] [--detail-top-n 50] [--emit-alignments] [--threads N] [--[no-]report] [--resume] [--progress]` is a **reference-free** clusterer over the Complete, non-fragment transcript windows (loaded via `align/map.py::_iter_demux_read_batches(only_complete=True)` — same substrate as the demux protein groupings). Pipeline: `dereplicate` (**hash-keyed**: groups on a fixed-width `xxh3-128` `fixed_size_binary(16)` of each window, NOT the raw string — at ~19M reads the ~18M distinct ~1 kb string keys overflow Acero's int32 distinct-key offset and abort with `std::length_error`; the representative is recovered via `pc.take` at each group's first row) → `encode`+`minimizers` (ASCII→uint8, canonical k-mer SplitMix64 rolling hash, window-min via boundary-masked `unfold().min`, zero-copy chunked iteration over the Arrow value buffers; **`--minimizers-per-seq` caps each sketch to its N smallest-hash minimizers** — a bottom-N MinHash, the dominant memory lever: 4.34B→~0.9B minimizers at N=50 on a 19M-read run) → `candidates` (sorted-index anchor-star with diagonal-consistency + high-frequency stop-word cap — high floor so small/expression-concentrated datasets aren't over-pruned, the star is already linear in bucket size, verify supplies precision) → `verify` (edlib HW, **shorter→longer**, accept iff identity ≥ `--identity` AND 5'/3' overhang ≤ thresholds; emits + caches the CIGAR — `task=path` is ~free, so **edlib runs once per edge**, reused by consensus) → `cluster_graph` (**scipy connected-components**, NOT radius-1 greedy: at ~1% error almost every read is a distinct unique with abundance≈1, so the roadmap's abundance-anchored greedy under-clusters; CC over the verified graph collapses all minor variants while distinct transcripts (>2% divergent) share no edge; centroid = highest-abundance/longest member) → `consensus` (**frame-anchored iterated CIGAR-walk PWM** via **numpy `bincount`** — kept torch-free so the per-cluster `ProcessPoolExecutor` workers don't deadlock on torch's OpenMP-after-`fork` poison; reuses cached CIGARs, re-aligns only the component-path members not directly verified to the centroid, capped at `_CONSENSUS_MAX_MEMBERS=20k`) → ORF on consensus (cached compiled regex + low-complexity guard so a chaining-artifact consensus can't make the overlapped-ORF regex pathological) → `quant` (`FEATURE_QUANT(feature_origin='cluster_id', engine='constellation_denovo')` + per-sample TPM). **Variant characterization (the "what was collapsed" deliverable):** `variants.py` calls within-cluster variants with a **context-aware, depth-gated error model** — the binomial (or beta-binomial when `--overdispersion>0`) upper-tail SF under a context-conditional null ε (homopolymer-indel by run length / substitution / non-hp-indel; explicit priors in `ErrorModel`, the hifiasm non-uniform-error insight), BH-FDR per cluster, `n < n_min → ambiguous`; the binomial `n` is raw read multiplicity (= the abundance-weighted PWM column sums). `--error-model empirical` re-fits ε from cluster-wide high-confidence disagreements (high depth, major fraction >0.95) and re-tests every variant position with no second consensus pass. `haplotypes.py` builds the read×variant-position allele matrix by projecting **every** cluster member onto the centroid frame (via `member_allele_row` — the cached consensus alignment when the member voted in the PWM, else a bounded re-align; capped at `_HAPLOTYPE_ASSIGN_MAX=50k` members with the abundance-tail folded into one all-uncovered bucket), so **haplotype abundances sum to the cluster's read count** (quant-grade — every read is assigned to exactly one haplotype, not just the ≤20k consensus-voting subset), collapses to distinct allele-combination haplotypes (abundance-weighted), and computes pairwise **r²** (phasing) → `max_linkage_r2` per variant. Haplotype **columns** are restricted to **`call=='real'`, in-core, base-substitution** variants (the FDR gate `call=='real'` drops positions whose minor mass is consistent with basecaller/PCR/RT error under the context-conditional null or too shallow to judge — otherwise one error read fragments a clean cluster into spurious haplotypes and dilutes their abundances; `in_core` drops the ragged 5'/3' coverage ramps; base — not gap — minor alleles drop terminal deletion/length-variation positions), so neither low-frequency error nor 3'-length-class noise splits reads into spurious haplotypes; the full variant catalog still records every tested position regardless of call. The `--overdispersion ρ` beta-binomial null is the tuning lever for what `call=='real'` means at high depth (a point-binomial over-calls sub-1% minor alleles once depth exceeds ~10k reads; ρ inflates the null variance by `1+(n-1)ρ`, capping effective depth at ~`1/ρ`). Outputs: `clusters.parquet` (TRANSCRIPT_CLUSTER_TABLE, `mode='de-novo'`, genome cols null, consensus + ORF populated), `cluster_membership.parquet` (per-read role + alignment-derived metrics: `match_rate` / `indel_rate` / `n_aligned_bp` / signed `drift_5p_bp`/`drift_3p_bp`), `cluster_variants.parquet` + `cluster_haplotypes.parquet` (new schemas in `cluster/denovo/schemas.py`), `cluster.fa` + `proteins.fasta` + `feature_quant.parquet` + `cluster_counts.tsv`, `diagnostics/report.md` (default-on aggregate); under **`--emit-cluster-detail` (off by default)** per-cluster `detail/cluster_<id>/{haplotype_map.svg, variants.tsv}` (the MSA-free **haplotype heatmap**); and under **`--emit-alignments` (off by default)** `cluster_alignments.parquet` (`CLUSTER_ALIGNMENT_TABLE` — the per-member CIGAR alignments to each cluster's centroid/representative frame that built the consensus PWM, for assembly QC / pileup reconstruction; the consensus shares that frame minus cluster-wide-deletion columns). The cluster manifest writes `align_dir=""` (no align dir; reference fields null). **Threshold note:** `--identity` is a read-to-read (pairwise) gate; two reads each ~1% from the true transcript are ~2% apart, so for ~1% error reads ~0.96-0.97 reduces low-abundance-tail fragmentation while the deep clusters are intact at 0.98 — `max_cluster_rounds`>1 (consensus-anchored re-clustering, the principled fix) is reserved. Parallelism: minimizers/candidates/PWM are torch-vectorized; verify + per-cluster consensus fan out via fork-based `ProcessPoolExecutor` with copy-on-write-shared sequence lists (no per-task sequence pickling).

**EM clustering (`cluster/denovo/em/`) — the full loop shipped; reachable as `transcriptome cluster --mode em-orf` / `--mode em-kmer`.** The components clusterer has nothing to anchor on: exact replication of whole reads is 0.15%, so abundance ≈ 1 everywhere and the roadmap's abundance-anchored greedy set-cover has no hubs. At the **ORF** level exact replication is 30% of reads. So ORFs become large, informed k-mers used for *seeding only*, and the clustering itself is an EM loop over whole reads (`seed → fold → E-step → M-step → refine`). A **template** is the sequence a read is aligned against: in round 1 a representative read's trimmed cDNA, in later rounds that group's consensus. The product is reference transcripts carrying ORF nodes with per-sample read support — proteoforms are a heuristic *inside* clustering, not its target.

*`em/seed.py`* — longest sense ORF (≥30 aa, ATG-only, forward strand) per read via the promoted `denovo/orf.py::best_sense_orf` (a leaf module both `pipeline` and `em` import, so there is no cycle); ORF prediction runs once per **distinct cDNA** (Layer-0 derep first) rather than once per read; ORF nucleotide strings are then dereplicated exactly on a fixed-width hash (same Acero int32-offset reason as `dereplicate`). Each distinct ORF elects one read whose full cDNA becomes the template, via a pluggable `--seed-representative` policy: `median-length`, **`longest-above-quality` (the `--mode em-*` default)**, `longest-template`, `most-5p-flank` (em-orf only), `most-replicated`. The policies and the election itself live in `em/elect.py`, shared with the kmer seeder. Default is the abundance-weighted *median* cDNA length rather than the longest, because the longest cDNA is the most likely chimera / concatemer / internal-priming artifact and electing it makes the template a low-support outlier — safe **only because** the consensus kernel can now extend past the frame's ends (before that a too-short template was an unrecoverable ceiling). **No replication filter**: Akap4's 849-aa proteoform was error-free in 4 reads and never twice identical, so any "seen ≥2×" gate erases it. Emits `SEED_ORF_TABLE` + a read→orf map.

**Round-1 seeding by read-level kmer clustering (`em/seed_kmer.py`, 2026-09-19).** The ORF seeder makes one template per distinct ORF and distinct ORFs scale ~linearly with reads (ledger #35), so it compresses only ~1.4x: at 9.39M reads, 3,778,760 templates / 6.12 Gb, a **13.95 h / 127 GB** round-1 E-step, and only 11.6% of those templates recruited anything. `em/seed_kmer.py::seed_by_kmer_clustering` runs the shipped `--mode kmer` kernels on the **reads themselves** (`dereplicate → extract_minimizers → generate_candidates → verify_candidates → connected_components`) and elects one read per cluster, emitting the same `TEMPLATE_TABLE` (minus the ORF — see below) so every stage downstream is unchanged. Measured on the same corpus at `identity 0.93`, ends `5' unbounded / 3' ≤ 100`, k15 w10 m100: **850,450 templates in 1.26 Gb** — 4.4x fewer templates, 4.9x fewer bases — and the partition it produces *before any alignment to a template* beats what the ORF path reaches *after* its E-step (gene dominance 0.866 vs 0.821, purity 0.985 vs 0.978, ARI 0.931 vs 0.560). Round 1 becomes **2.89 h / 26 GB** while assigning **more** reads (98.6% vs 96.2%) at equal gene agreement (0.980 vs 0.981), for 2 points of transcript agreement and 11 of transcript template recall. **The ORF path is not on the cost/quality frontier at all**: the *shipped* kmer gate (`0.98 / 30:30`) costs the same 14.07 h and beats ORF seeding on every outcome, so this is not "cheaper but worse" — kmer seeding dominates at equal cost, and relaxing identity/ends then buys the 4.8x cut separately. It also removes a correctness failure rather than only cost: against the ORF set the median read has **659 candidate templates and 11.0% of reads hit the `-N` cap** — what `_warn_on_saturation` calls unsound rankings — against 84 and **0.05%** for the kmer set.

*The grouping order and the template election are separate decisions, and the sweep conflated them.* One "rule" drove the minimizer bucket anchor, the component centroid order **and** which read became the template, which forced a choice between the best partition (`abundance`: gene dominance 0.866, elected rep median error 0.0050, 72% clearing Q22) and the best-sequenced representative (`qlen`: 1.7x the templates, rep median error 0.0040, 97% clearing Q22). Constellation splits them: the grouping keeps the shipped abundance order, and the template is elected by the EM's own `--seed-representative` policy over the cluster's members, so `ComponentResult.centroid_uniq` is computed and deliberately discarded. **This combination is not yet measured** — `section_seeding` reports `seed_quality_median` / `seed_quality_ge_floor_frac` precisely so the full-scale run checks it against those two numbers. Related negative result (ledger #51, worth recording so it is not retried): **linclust's longest-read bucket centre is the wrong anchor here** — at 9.39M, `abundance` 0.866 vs `length` 0.815 vs `qlen` 0.806, because anchoring on the longest read pairs the most length-discordant reads in each bucket, exactly the pairs the overhang gate rejects. At 1M the three converge, so a 1M-only experiment calls it a tie.

*The 3' cap is load-bearing and its failure is invisible below full scale.* With `components` + unbounded ends, 9.39M reads put **7,096,457 (76% of the corpus) into ONE component at purity 0.154**; `500:500` still leaves a 410,660-read one. The same settings at 1M peak at 328k, and the existing `_MEGA_CLUSTER_UNIQUES = 2_000_000` guard counts *uniques* so it never fired. `seed_by_kmer_clustering` therefore counts **reads**: warns above 1% of the corpus (real data at the shipped gate peaks at 0.83%), and **fails the stage** above `--max-seed-cluster-frac` (0.25). Both thresholds also require `--min-chain-cluster-reads` (10,000) in the cluster, because a fraction needs a corpus to be a fraction *of* — three transcripts at 20x each put 33% of the reads in every cluster, correctly, and the entire evidence base for these numbers is at 9.4M reads. `--seed-grouping greedy` is the chain-proof fallback (largest cluster 60k vs 7.1M) at ~1.4x the templates and 10 points of contiguity.

**The M-step has no minimum protein length (2026-09-19).** `gated_orf` took a `min_aa_length` and `MStepParams` carried it from `--min-aa-length`; both are gone. Two reasons, and the second is the one that made it a defect rather than a preference. (1) The M-step's job is to report the protein each node's consensus *encodes*; a length floor there is a claim about biology imposed on a measurement, and the caller can filter. (2) **It leaked into the algorithm.** Each node's ORF interval carries forward as the next round's template `orf_start`/`orf_end`, which `gated_orf` reads as its **certified-by-construction** interval — so a protein-annotation knob was setting how conservatively later rounds gated their own ORFs. Removing it is **monotone**: `best_sense_orf` keeps the longest ATG→stop per `(frame, stop)` and takes the global max, and the longest for a given stop is its earliest in-frame ATG, which does not depend on the floor — so lowering it can only *add* short ORFs where there previously were none, never change a long one. Every M-step test passed unchanged, which is the evidence. It also stops erasing real proteins: Prm1 is 51 aa against the old effective floor of 60 (ledger #6). `_NO_LENGTH_FLOOR = 1` is how "no floor" is spelled, because `best_sense_orf`'s regex needs *a* bound and ATG-plus-stop is the shortest ORF there is.

**`--min-aa-length` now means exactly one thing per mode.** It was three parameters wearing one name. **em-orf**: the seeding key, and nothing else — default **30**, not the parser's old 60, because at 60 the seeder cannot make a template for a 51-aa protein. **kmer**: the protein-annotation floor on each consensus in the (separate) de novo pipeline, default 60, unchanged. **em-kmer**: refused — that seeder predicts no ORF and the M-step has no floor, so the flag would have no effect and a silent no-op makes a run look like evidence about a parameter that did nothing. The parser default is `None` and each handler resolves it, the same treatment `--identity` and `--overdispersion` get.

*The ORF is annotation under kmer seeding, not part of the algorithm.* Under ORF seeding the ORF is the **key** — a template exists because a distinct ORF did, so `--min-aa-length` is a seeding parameter there. The kmer seeder partitions on read sequence similarity, the M-step splits on column covariance, and round 1 ranks on cluster support + seed quality, so nothing in the loop consults an ORF: its templates ship `orf_start == orf_end == 0` and **no ORF is predicted at seed time**. That is load-bearing rather than an omission — `mstep.gated_orf` treats the seed ORF interval as *certified by construction* and declines to judge it, so predicting one at seed time would silently **relax the M-step's support gate** on the strength of a claim the seeder never made. `(0, 0)` is the honest statement, and it makes the gate judge the whole ORF. Proteins are predicted per NODE on its own consensus, with no length floor at all (see above); `min_aa_length` is consequently absent from the kmer seed stamp and refused as a flag under em-kmer.

*Seeding only, no consensus after round 1.* Median read↔best-template identity is 0.992–0.994 for every kmer set, so admission at `p_floor = 0.97` is nowhere near binding and template *error* is not what limits recruitment. The real gap is template *extent* (median reference coverage by the elected template 0.31–0.44), which a consensus over cluster members would not fix either — it needs the M-step's extension machinery, which already exists.

*Shared election (`em/elect.py`).* `RepCandidates` / `REPRESENTATIVE_POLICIES` / the two-pass group-statistics-then-rank election moved out of `seed.py` into a leaf both seeders import, so `--seed-representative` provably means the same thing under either mode (`seed.py` densifies its ORF hash and calls the same `elect_representatives`, bit-identically). **`most-5p-flank` is em-orf only** — it ranks on `orf_start`, which kmer seeding has not predicted at election time, and predicting an ORF per unique cDNA is the 9.15M-call cost it exists to avoid; it raises rather than substituting. The ORF fork-pool moved to the leaf `denovo/orf.py::predict_orfs_parallel`, called once per unique cDNA (~9.15M) for ORF seeding and once per *elected template* (~0.9M) for kmer seeding. And `best_quality_per_uniq` now indexes positionally: `dereplicate` builds `read_map` column-wise from `reads`, so row *i* of one is row *i* of the other and the `pc.index_in` over 9.4M read ids it used to do bought nothing (`assert_read_map_alignment` is the guard).

*The CLI surface.* `--mode {genome, kmer, em-orf, em-kmer}`; bare `em` resolves to `em-orf` with a note (under-specified, not wrong) and `genome-guided` / `de-novo` keep warning as deprecated aliases. **The `mode` column stays `"em"`** — the mechanism is the EM loop and the seeder is a parameter of it — so `CLUSTER_MODES`, `clusters.parquet` and the viz colour maps are untouched, and the eventual `--mode em --seeding kmer` consolidation is a pure CLI change. **The default does not flip**: kmer seeding dominates on every measured round-1 axis, but the multi-round comparison that would justify the flip is the reason this exists, and flipping first destroys the baseline it is measured against. `--identity` / `--max-5p-overhang` / `--max-3p-overhang` are shared with `--mode kmer` and default to `None`, resolved per handler (0.98/30:30 for kmer, 0.93/inf:100 for em-kmer) — the same treatment `--overdispersion` already gets, and for the same reason: one flag with two right answers holds neither. The overhangs accept `inf` / `none` / a negative value, mapping to `verify.UNBOUNDED_OVERHANG` (the gate is a plain `overhang > max` comparison, so a value no real overhang reaches *is* unbounded, with no kernel branch). A flag the active mode ignores is an **error**, not a silent no-op (`--fold-identity` under em-kmer, `--identity` under em-orf), matching `predict-library`'s EncyclopeDIA-only flags under `--backend koina` — a swept parameter that did nothing makes the run look like evidence about it. `--min-shared` / `--diag-span-max` are exposed for the first time (ledger #4), defaulting to the measured `(2, 20)`: `min_shared=3` costs 2–10 points of gene contiguity, `diag_span_max=60` buys ~1 point over 20, so the diagonal span is the one worth relaxing.

*Resume across a changed seeder is refused.* `seed/params.json` stamps the fields the seeder actually reads (per mode, so a changed `--rounds` does not invalidate it) and `_loop` checks it on **every** resume, not only the ones that rebuild the seed stage — a resume restarting at round 4 is just as committed to the original seeder as one reusing `seed/` directly, and checking only the latter left the former running one seeder's templates under the other's manifest. A `seed/` dir with no stamp predates this and can only be ORF-seeded, so resuming it as kmer is refused by name.

*`em/fold.py`* — runs `extract_minimizers → generate_candidates → verify_candidates` on the ORF nucleotides with **unbounded end tolerance** (under edlib HW the whole shorter query always aligns inside the ref, so a contained fragment ORF passes the *identity* gate and must be rejected by **classification**, not by an overhang threshold — one verify pass serves both rules), classifies every accepted pair, and groups the folding edges with the new `cluster_graph.py::greedy_set_cover` (abundance-ordered, **radius 1**, ledger #18 — a claimant takes only its unclaimed direct neighbours so groups cannot chain: largest group 2,889 vs 5,743 for components over the identical edge set at equal purity). **Rule 1 (error variants)**: `|Δlen| ≤ 9` and `(n_insert − n_delete) % 3 == 0`. **Rule 2 (frameshift pairs, `--fold-frameshifts`, default off)**: `n_insert == 0` ∧ `n_mismatch ≤ 3` ∧ exactly one indel run ∧ net frameshift → collapse into the more-replicated form and declare a variant column. Off by default because collapsing a frameshift pair merges two proteoforms whose proteins differ downstream of the indel — a much stronger claim than merging error variants — and the E-step reaches the same result without it. **Everything else separates**, including contained-without-indel pairs: at the ORF level a 5' truncation and an alternative start are indistinguishable, so the E-step decides them against the full cDNA. **There is deliberately no template-level fold** — two real Akap4 proteoforms are 0.9735 identical because a 130-nt unrelated first exon only costs 2.65% under edit distance, so a template-level fold merges them.

Three corrections to the design spec, implemented as corrected and pinned by tests: (1) an ORF string is ATG→stop inclusive so its length is **always** a multiple of 3 — `Δlen % 3 == 0` holds identically and rule 1's mod-3 clause actually tests the *terminal overhangs*, with the discriminating power in `|Δlen| ≤ 9`; (2) rule 2's "shorter fully contained in longer" is **vacuous** under HW, the discriminating clause is `n_insert == 0`; (3) `verify._order_pair` breaks length ties by `uniq_id` and `Δlen == 0` is modal under a ±9 bound, so the tie-break fires constantly — rule 1 is symmetric under the swap, rule 2 is not and is written against `(uniq_short, uniq_long)`. Also: `verify_candidates` gains `min_budget` (default 0, off) because a pure fractional gate is unusable on short sequences — at identity 0.97 a 30-aa ORF (93 nt) gets `int(0.03 × 93) = 2` edits while two reads each at ~1% error differ by ~1.9 bases in expectation, so genuinely-same-proteoform short pairs fragment into singletons. Measured on a synthetic 30-aa ORF with three substitutions: 4 groups at budget ≤2, 1 group at budget 3.

*`readers/paf.py` + `em/estep.py`* — PAF parsing did not exist anywhere in the repo (the registered reader raised `NotImplementedError`). Now two layers: `iter_paf_batches` is the streaming primitive, accepting a path **or a live pipe** (minimap2 stdout) and yielding `PAF_RECORD_SCHEMA` batches, and `PafReader.read` projects into `ALIGNMENT_TABLE` per that schema's own docstring, folding query clipping back into `cigar_string` so `q_start` round-trips through `align/cigar.py::query_start_from_cigar`. Parsing is **vectorized numpy buffer surgery** (newline/tab offsets via `flatnonzero`, columns as zero-copy Arrow string arrays cast in one shot, tags via `pc.extract_regex`): with `--secondary=yes -N 50` every read emits up to 51 lines — ~51M (~6 GB) at 1M reads, ~510M at 10M — where a `for line in fh` loop is ~17 min/round of pure Python and the exact anti-pattern the resolve-stage rules forbid. Batch boundaries carry a partial tail forward so output is independent of `chunk_bytes` (tested 7 B → 1 MB). `minimap2_stream` joins the generic wrapper beside `minimap2_run`. The E-step assigns by `AS:i` inside an **absolute** band with a ranked tie-break (node weight → ORF length → score); `rank_banded_candidates` is pure and vectorized over a whole batch, so the band's operating point is testable from hand-written hits **with no minimap2 on `$PATH`**. Two more spec corrections: (1) the band is *not* what makes nested templates visible — a template that is another plus a 130-nt 5' exon scores ~260 AS apart, which a 40-point band excludes just as surely as the stock `-p 0.8`; `--secondary=yes -N 50 -p 0.05` is what makes it reportable at all, and the band's real job is arbitrating among comparable-scoring templates (absolute, because a ratio is too tight on a 400-nt transcript and too loose on a 5 kb one); (2) fractional tie weights stay **inside the model** — `CLUSTER_MEMBERSHIP_TABLE` is one row per (cluster, read) and `cluster_counts.tsv` writes `int(v)`, so `--tie-resolution fractional` drives node weights and the M-step PWM while reported membership and quant still come from the argmax. Reverse-strand hits are dropped as a **correctness** requirement: on a `-` hit PAF reports `q_start` on the forward query while the CIGAR is against the reverse complement. `run_estep` refuses above a template-bases ceiling rather than silently using a multi-part index, whose per-part `-p`/`-N` filtering and primary/secondary calls are not comparable across parts.

*`em/mstep.py` + `em/columns.py` + `em/covariance.py`* — pooled folded consensus → candidate columns → covariance → one node per observed **state-tuple** → ORF re-predicted under a **support gate**. Order matters: the pooled PWM comes first because round 1 has no declared columns to group by. Round 1 needs **no alignment work at all** — minimap2's `cg:Z` is already a read→template alignment in exactly `project_member`'s convention, so `specs_from_assignments` feeds it in with `frame_start=t_start`, `member_start=q_start`, and the soft clips become extension candidates; only post-splice passes call edlib. The support gate certifies **consensus** columns (where gap-winning columns don't exist, resolving a spec ambiguity) on base coverage — A/C/G/T votes only, since at a ragged end many members vote a deletion so *total* coverage stays flat while base coverage ramps down — and truncates an ORF reaching past the seed boundary at the last certified codon, flagged. It is only meaningful because the kernel can now extend past the frame at all. The round loop that iterates these now exists — see the EM-loop section below. Every annealing knob (`eps_floor`, `overdispersion`, `f_min`, `q_candidate`, `q_edge`, `gamma`, `max_nodes`, `min_node_reads`) is an explicit per-round argument on `refine_template`; there is **no `**kernel_kwargs`**, because a forwarded `**kwargs` is how `--consensus-max-passes` survived as a user-facing flag that did nothing for a release.

**The EM round loop (2026-09-15).** `seed` / `fold` / E-step / M-step all shipped and *nothing iterated them*, so none of it was reachable from the CLI and its policy could only be measured by a driver outside the package. `em/rounds.py::run_em` is that engine, wired as **`transcriptome cluster --mode em`**. Per round: `templates → E-step → assignments → M-step → nodes → refine → templates`, converging on the **lineage-aware** read-switch fraction (a read that moved only because its template *split* has not chosen differently, and counting it would leave the loop looking unconverged forever). Every round is `_SUCCESS`-gated and every artifact addressable, so `--resume` restarts after the last complete round; template ids are `(round << 40) | row` rather than a counter, which is what lets a resumed round rebuild identical ids, and a round whose successor templates were never written rebuilds them from its own nodes.

*The assignment rule — one candidate pool, two ranking regimes (`em/scheduler.py`).* The **pool** is `n_match / aln_len ≥ p_floor` (0.97) every round — the first **absolute** quality gate the pipeline has had. The rule it replaces banded relative to each read's *own* best hit, so a read's worst match was admitted whenever it was its only match, and that read then entered the PWM of whatever it landed on: the mechanism by which an errored template's consensus gets built in the first place. Identity rather than AS because AS/span charges an inserted base **8** where a substitution or deleted base costs 6, so an AS floor rejects insertion-carrying reads it should admit. Reads with no admitted hit are emitted with `template_id = −1` rather than forced somewhere, so the rejection rate is visible per round.

**Round 1 ranks on ORF replication, then seed-read `dorado_quality`** — not on score, and this is load-bearing rather than a preference. Every round-1 template is a single errored read, so a score measuring "how close is this read to that read" cannot separate signal from the ~1% error both copies carry; worse, argmax-AS returns each read *its own seed* by construction (perfect self-identity ≈ 2L against ≈ 1.94L for the gene's true consensus — a ~72-point gap at 1.2 kb that no near-tie window reaches), so self-capture would be total and permanent in every round. Measured on a 4-transcript synthetic panel: **94 of 103 round-1 templates recruit nothing and stop existing**, with no prune and nothing deleted.

**Round 2+ ranks on a log-likelihood over the *differing* positions** (`em/likelihood.py`), because AS and percent-identity both put the ~97% of identical sites into the denominator and dilute the handful that discriminate. Under a *uniform* ε that reduces to what AS already does — the entire win is that nanopore error is not uniform by type, so a homopolymer-length call is weak evidence and a substitution is strong where AS charges both ~6 points. Three terms: matched bases (what stops a short perfect alignment beating a long near-perfect one), the differing positions, and read bases the template does not explain; indels are charged per **run**, not per base. Abundance returns only as an escape — a more abundant candidate wins **only** within `--near-tie-delta-logl` (5 nats ≈ one discriminating substitution) **and** at `--support-ratio` (20×) the support — so a real variant with two clean positions is outside the window and cannot be absorbed however abundant the neighbour. **Caveat recorded in the module:** the shipped `ErrorModel` returns 0.0103 at a 5-base homopolymer against the **0.22** the bench measured there, which is 21× low and shrinks the homopolymer-vs-substitution margin from ~4.3 nats to 1.23. The ordering still holds; the separation is a third of what the data supports. Not fixed by inventing a slope from one measurement (ledger #40) — a refitted model sharpens it for free, and the shared default is left alone because `call_variants` uses the same object.

*No prune, no merge.* The handoff's §4 and ledger #34 call a support prune a prerequisite, on the reading that t302020 (Tuba1a — 1,371 reads on a 21-stop sequence) was a single read's own sequence promoted to a template. **The cause established since is different**: its consensus ORF was *contaminated* by reads that should never have entered the PWM, which is exactly what `p_floor` fixes. So a read was sequenced, it is real, it is just not like anything else — it is kept as a lowly-supported transcript and the scientist decides. A template disappears exactly one way, and it is a consequence rather than a rule: **one that recruits no read emits no node.** Merge is dropped for the same reason it existed — ledger #25 is explicit that "the between-round merge is the structural fix" for self-capture, and the round-1 rule removes that at the source. Both worked examples resolve without it (Tcp1 by the covariance M-step; H3f3b's elongated frameshift template loses round 1 outright to the more-replicated correct form). What remains is `refine.detect_redundant_templates`, which **reports** the pairs a merge would have collapsed so that dropping the operation is checkable rather than assumed; `asm5` there rather than `map-ont` is a preset-to-problem match (k19/w19 is ~16× more specific and samples ~2× sparser, which accurate ≤5%-divergent sequences can afford), and `-c` is mandatory or PAF column 10 is chain anchors and a 0.995 threshold means nothing.

*`-N` is a correctness parameter, not a cost one.* The pool must contain **every** template within `p_floor`, because both rankers assume it and minimap2 truncates by **score** — among near-clone templates score differences are 1–2 units, so a truncated pool is close to an arbitrary sample of the set being ranked. That is an answer to a different question, not a slightly worse one. So `-N` left `TEMPLATE_MINIMAP2_ARGS`, defaults to **500**, and every assignment row carries `candidate_cap_hit`; a non-trivial rate **warns loudly**. The separate hard-coded 3 Gb `max_template_bases` ceiling is **gone** — it was a second, unstated scoping number that fired ~5× below where the single-index-part argument bites, and at 9.4M reads it forced `--min-seed-reads 2`, which erases minority proteoforms before they can be tested at all. The `-I` check remains and now carries both reasons it exists: a multi-part index double-counts read mass **and** breaks the query contiguity the block reducer's grouping depends on.

*Seeding gained a quality term* (`--seed-representative longest-above-quality`, the `--mode em` default): the longest cDNA clearing Q22, falling back to the group's highest-quality read. The trade this appears to need does not exist — Spearman(length, error) is +0.015 to +0.049 in every length stratum, so length and accuracy are independent — and as accuracy selectors they are not comparable: top decile by `dorado_quality` gives median error 0.00114 (0.25×), by **length** 0.00501 (1.10×, *worse* than random). Quality is the floor because its benefit saturates (Q22 is the knee of the decile curve); length is the objective because its cost does not. `dorado_quality` now rides from `READ_TABLE` through `_iter_demux_read_batches` into the corpus, presence-guarded like `quality`.

*Data architecture — nothing read-cardinality in Python.* The corpus is written once as an Arrow IPC file plus a FASTA and **mmapped** by every round and every worker (`em/corpus.py`). Measured, the prototype's `dict[read_id, str]` approach does not survive a fork: a child touching 14% of a 1.5M-entry dict privately dirties **845 MB**, against **8 MB** for the same access through a memory-mapped buffer. **Reads and templates are named in their FASTAs by row index**, which is the keystone — PAF's `q_name`/`t_name` parse as integers straight out of the byte buffer, read grouping is `np.diff` on int64, the row index needed to look a sequence back up rides along free, and `read_id` is materialised exactly once per round, on the winners. `em/paf_scan.py` decodes the six fields every row needs and defers the rest to the winners (42 → 122 MB/s, 2.9×; at 216 GB/round that is 85 → 29 min), carrying partial read-groups across block boundaries as **raw bytes** so nothing decoded crosses and grouping is independent of how the pipe chunked. The M-step fans out with units bin-packed **largest-cost-first** (the prototype's static contiguous ranges left effective parallelism at ~2–3 of 8 because a mega-template serialised its chunk); measured at load imbalance 1.000 for 200k templates into 832 units, and **60.6** if one 500k-member template is inserted — which is what `--max-members-per-template` exists to bound, since no packing splits a single unit of work. Workers open the corpus and templates themselves rather than inheriting them, so the design is correct under `spawn` too. **No torch below the fork**: `consensus` / `columns` / `covariance` are numpy-only because the parent has already spawned torch's thread pool during minimizer extraction and a torch op after `fork()` deadlocks on OpenMP — a silent hang, not an exception.

*Two free fixes in `readers/paf.py`* found while benchmarking, which help every PAF consumer: `_split_fixed_columns` built a `pa.py_buffer(buf.tobytes())`, never referenced it and deleted it 47 lines later (a full memcpy of every block), and it located each row's first tab by searching ~11× more tabs into the rows instead of the rows into the tabs (57 ms → 4.7 ms per 200k rows, same answer). Together: 47 → 76 MB/s.

*`--mode` is named for the mechanism.* `{genome, kmer, em}` replaces `{genome-guided, de-novo}`, which described provenance; both old spellings stay accepted as deprecated aliases that normalise and warn. The `mode` **column** follows the flag, and the vocabulary **widens rather than replaces** — pre-rename values still load and the viz frontend's colour maps keep entries for both, so no clusters.parquet needs migrating.

*`em/estep.py` is superseded and marked so.* Its rule is replaced by `em/scheduler.py` (the rule) + `em/assign.py` (the reducer) + `em/paf_scan.py` (the decoder), and nothing in the library imports it any more. It is **kept rather than deleted** because it still carries two capabilities the new path does not, and deleting it would turn that into a silent regression: `tie_resolution="fractional"` (splitting a read's mass across its banded templates by `node_weight` to drive the M-step PWM while membership and quant still come from the argmax — library-only, never CLI-reachable) and `emit_coverage` / `READ_ORF_COVERAGE_TABLE` (the non-exclusive (read, template) ORF-coverage view the later graph stage wants, deliberately not emitted during rounds because it is one Python CIGAR walk per *banded* pair, 50–90M per round at 9.4M reads). Restoring either onto the new path is small; doing it inside the old module is not, because the ranking it is wired to is gone.

**Review-driven corrections to the EM loop (2026-09-15).** An external review found eleven defects, all reproduced and all with regression tests verified to fail on the parent commit. Four were P1, and three of those were in the final-output path — the part with the least test pressure because it runs once.

*A split parent collapsed into one cluster.* `build_cluster_tables` keyed read→cluster on a `{parent_template_id: cluster}` dict, but a parent can emit several nodes and the dict kept only the last: a parent splitting 3/2 exported as **0/5**, with the first child holding no reads and no representative. The M-step knew the answer and discarded it — `_node()` receives the member indices and `RefinedTemplate` did not carry them. It does now, the worker emits a `NODE_MEMBERSHIP_TABLE` shard keyed on `(parent_template_id, haplotype_id)` (unique within a round and known at emission, where the child's eventual `cluster_id` is not), and the output builder joins on that. The general lesson: read→*template* is not read→*cluster* once the M-step is allowed to split.

*Quantification pooled every read into `sample_id = -1`.* Sample ids came from an optional `samples=` argument the round loop never passed, while the assignment table carried the real ones the whole time. Per-sample counts and TPM were silently wrong.

*The member cap took a prefix, not a sample.* It sorted by weight — but under the current rule every assigned read has weight 1.0, so a stable sort over ties returns the first `max_members` rows in table order. A 60/40 variant mixture loses the minority entirely, i.e. exactly the population the pipeline exists to keep. Now a uniform random sample, seeded per template so a re-run and a resumed run agree.

*`TemplateStore` built the whole homopolymer context on open* — as int32, in the E-step reducer **and in every M-step worker**, none of which touch it. Measured: 4 MB of sequence peaked at 112 MB, and at 4 bytes per template base round 1's ~6.2 Gb wanted **~25 GB in each of ~52 workers**. Now lazy (opening is free), `uint8` (the ε table saturates at 64, so capping at 255 is not a truncation into a wrong context), and built in blocks cut on template boundaries — where a run cannot straddle, because that is the reset. Unchunked, 48 MB of sequence peaked at 1,584 MB; chunked, 304 MB, and the ceiling is the block rather than the corpus.

Six P2s, each a case of something being invisible rather than wrong-looking: reads minimap2 never reported produced no PAF line and so vanished from the rejection accounting entirely (now explicit `template_id = −1` rows plus an `n_unmapped` counter); convergence measured only over reads assigned in **both** rounds, so losing half the assignments scored zero churn as long as the survivors kept their lineage — the stopping rule now reads `frac_unsettled`, over reads assigned in *either*; the packed lineage key `(child << 21) ^ parent` overlapped the two ids past 2²¹ rows, which round 1's ~4.17M templates reaches, reporting an unrelated switch as inherited (replaced with an exact structured-dtype pair comparison); resume trusted a template file that merely existed, dying on a truncated one instead of rebuilding from the round that finished; resume also reset previous assignments and overwrote `churn.tsv`, losing both the resumed round's churn measurement and the whole run's history; and a completed run had no `manifest.json`, so `read_manifest_dir` rejected it and the viz layer could not attach it however well-formed its parquet was.

**The 1M-read OOM: a unit pickled the whole round (2026-09-16).** 100k reads ran; 1M died at 230 GB. The cause was not memory *usage* anywhere — it was what crossed the `ProcessPoolExecutor` boundary. `iter_unit_batches` built each unit as `pa.concat_tables` of one slice per template, which gives **one Arrow chunk per template**, and every chunk holds a reference to the whole parent buffer. Pickling therefore serialised the parent **once per chunk**, so the payload scaled with the *number of templates in the unit* rather than the rows it contained. Measured on the real 1M data: **90.3 GB per batch for 1.4 MB of content**; reproduced here at 1,991x on a 200k-row stand-in.

It explains all three observations from first principles: 100k never failed because its sorted-assignment table is a tenth the size; 582 templates/unit x 0.16 GB predicts the observed 90.3 GB; and lowering `--mstep-workers` made it *worse*, because `n_units = workers x units_per_worker`, so fewer workers means more templates per unit means a linearly larger pickle. The fix is `combine_chunks()` on each unit before it is yielded — materialising the unit's own rows into contiguous buffers — plus a projection to the six columns the worker actually reads, after which every unit together pickles to less than the source table.

**And the corollary, which is a rule rather than an incident: `combine_chunks()` allocates even for a SINGLE chunk** (measured 32.2 MB for a 32.2 MB array, against 0 for `chunk(0)`). `TemplateStore.open` used it to normalise the sequence column, so every M-step worker copied every template base — a real per-worker floor, though not the failure. It now views `chunk(0)` when the column is already contiguous, and `write_templates` emits **one record batch** so there is a contiguous column to view (a templates table built from the M-step's node shards has one chunk per shard). Opening a store went 30.0 MB → **0.0 MB**. `ReadStore.open` was already free and now has a test saying so.

The generalisable lesson for anything that forks: *a zero-copy slice is not a zero-copy **payload**.* Arrow slicing and chunking are cheap in-process precisely because they share the parent buffer, and that is exactly what makes them expensive to serialise. Anything handed to a worker should be `combine_chunks()`-ed and column-projected first, and the regression test to write is on the **pickled size**, not on wall time or RSS.

**`pc.take` on a chunked column is not a lookup, it is a concatenation (2026-09-18, ledger #47).** `ReadStore.take_sequences` was one line — `pc.take(self.sequence, rows).to_pylist()` — and its docstring claimed the access was "bounded by design… never the whole corpus". The *output* genuinely was bounded; **residency was not.** `pyarrow.compute.take` concatenates every chunk of a ChunkedArray before indexing, so the cost is the whole column however few rows are asked for. Measured on a 232 MB / 48-chunk mmapped corpus, fetching **one** row: peak RSS **+444.8 MB** — about twice the corpus, the concatenated copy plus the paged-in source — against **+5.1 MB** taking chunk-locally. At 9.4M reads the corpus is ~25 GB, which is ~47 GB per worker on first access, in *every* worker: a lazy file-backed corpus turned fully resident, and what OOM'd the 48-worker run.

Do not confuse this with the pickle defect above, which was fixed separately. They are distinct, and the distinction matters for diagnosis: at 1M reads the corpus is 1.4 GB so this cost ~2.7 GB/worker — a real floor, never the thing that killed a run — while the pickle bug was ~90 GB per *batch*. The same analysis that found the pickle bug initially over-claimed this one; the corrective was that a floor which scales with the corpus and a payload which scales with the template count fail at different places and for different reasons.

`corpus.chunked_take(column, rows, chunk_starts)` is the fix: resolve each row to `(chunk, offset)`, visit each hit chunk once, restore input order. It is used by `take_sequences` and by the new `take_read_ids` — because the same defect was live at **three** sites, not one: the E-step reducer took `read_id` off the chunked corpus once per PAF block. The regression test is **structural, not a memory threshold**: `pc.take` must never be handed a multi-chunk column at all, asserted by spying on it, so it cannot go quiet under a different allocator.

**A third review of the EM loop (2026-09-19).** Seven findings, all real, all with regression tests verified to fail on the parent commit. Two P1s, and one of them was self-inflicted by the previous round's own fix.

*The member cap bounded what the cluster CONTAINED, not just what its consensus was built from.* `--max-members-per-template` exists so one mega-template cannot serialise an M-step unit — no packing splits a single unit of work — and it samples uniformly for exactly that reason. But membership was emitted only for the sampled reads, and exported counts and quant are both **counted from membership rows**, so a 20-read template capped at 5 exported 5 members and reported `n_reads = 5`. Scaling `node_weight` by the sample fraction repaired neither number, because neither reads it. Membership now covers every assigned read — unsampled reads go to the major node, which is what a uniform sample over an exchangeable tail licenses — and `n_reads` / `node_weight` are counted from membership rather than carried off the sampled node.

*`combine_chunks()` is a no-op on a single chunk, so the pickle fix missed the unit holding ONE template.* One slice in, one chunk out, parent buffer still attached: measured **60.4 MB pickled for 6 KB of content**. Not an edge case — LPT deliberately packs the biggest templates alone, and the live-template count can fall below the requested unit count. `take` detaches where `concat + combine` does not (0.0065 MB against 60.6 MB on identical content), so units are **gathered**, not concatenated. The narrower statement of the rule: `combine_chunks` is not a detach operation; it is a *contiguity* operation that happens to copy when there is more than one chunk.

*And the `chunk(0)` fast path that stopped every worker copying the template corpus read the wrong row.* `Array.offset` is not zero after a slice, and `chunk(0)` on a sliced ChunkedArray preserves it, so indexing the offsets buffer from 0 returns a different row — silently, with a plausible sequence: `["AAAA","CCCC","GGGG"].slice(1,1)` held `"CCCC"` and read back `"AAAA"`. Everything downstream would have been reading one template's bases under another's id. This is the cost of the zero-copy discipline stated plainly: the operations that avoid a copy are the ones that keep a *view*, and a view carries an offset that the buffer does not.

The four P2s are one shape — **an artifact from an earlier attempt that nothing marks as stale, read back by the next run as if it belonged to it.** Assignment shards are numbered from zero each time and the reader globs the directory, so an attempt that crashed after 40 shards followed by one writing 31 left 9 of the dead attempt to be read as this round's; the shard set is now replaced rather than overwritten into, which is safe because a retried E-step re-runs minimap2 from scratch. `_SUCCESS` was written *before* `lineage.parquet`, so a kill in between left a round claiming completeness without the one file the next round needs to tell a split from a genuine switch — refine now precedes the marker, the write is atomic, and recovery tests whether the file **opens** rather than whether it exists (a parquet is readable only once its footer lands, and declining to rebuild a half-written one is precisely what made the resumed round die). The corpus cache was keyed on nothing but its own existence, so a resumed run pointed at a different `--demux-dir`, or asking for a different `--max-window-length`, silently analysed the reads already on disk while the manifest recorded the parameters that had been *asked for*; both are now persisted and a mismatch is **refused** rather than rebuilt, because the corpus is the run's whole substrate and a mistyped path is likelier than a deliberate change. And `proteins.fasta` / `cluster.fa` / `feature_quant.parquet` are each conditional, so a run producing none of them left the previous run's in place, describing results that no longer exist.

The general rule, alongside the pickle one: *Arrow's cheap operations are cheap in a particular direction.* Slicing and chunking share the parent buffer, which makes them free in-process and expensive to serialise; `take` on a chunked column is free to *write* and expensive to *run*. Neither cost is visible in the shape of the call, and both are invisible until the corpus is large enough — so the thing to assert in a test is the **mechanism** (what was called with what), not the symptom.

*Measured end to end* on a 4-transcript / 160-read synthetic panel at 1.2% error: round 1 103 templates → 9 holding reads (purity 1.000, contiguity 0.881); round 2 → 7 (contiguity 0.981, churn 0.101); round 3 churn **0.000**. Still unverified at scale — the numbers that decide the design are the **saturation fraction at `-N 500`** (if non-trivial, `-N` is still too small and nothing downstream is trustworthy) and round-1 E-step wall time (~26 h projected at 9.4M reads, which is what staged depletion would address).


**M-step v2: covariance-driven refinement (2026-09-13).** Six EM rounds on the full 9.4M-read mouse testis dataset recovered most major RefSeq sequences but showed the M-step corrupting the templates it emitted, with reads scrambling between rounds instead of settling: references inflated 1,558 → 2,346 nt while their median ORF shrank 543 → 501; 28.1% of minor nodes (1.24M reads) differed from their major **only at uncovered positions**; 71.7% of the rest differed at exactly one position and 86.5% of differing characters were indels; 43.4% of templates carried ≥2 separated 5′ start modes, which `_core_region` trims as terminal raggedness. The replacement makes covariance the organising principle: **a column earns a node only by co-varying with another column.** That kills homopolymers with no special case, and lets coverage extent compete with allele on equal terms — which is what finally produces different-*length* references. It has a stated cost, accepted deliberately: a lone real frameshift with no covarying partner dies the same way, so the H3f3b readthrough node is no longer created and ledger #22 is reversed.

*`columns.py`* — candidacy by one of two routes, where candidacy is only permission to be *tested*, not retention. **Allelic**: `minor_frac ≥ f_min` **and** `n_minor ≥ a_min` **and** BH-significant under `survival(n_minor, depth, ε, ρ)`. Both halves are load-bearing in opposite depth regimes — at 20 reads one basecaller error *is* a 5% minor allele; at 1,525 reads a 1% null admits everything, so ρ (a beta-binomial capping effective depth at ~1/ρ) defaults **on** here at 0.01 and stays off in `call_variants`. **Coverage**: `uncov_frac` or `uncov_frac_local` in `[f_min, 1−f_min]`. The spec specified local only; measured, each denominator misses the other's case — a fused template covered by disjoint read sets is a *step*, not a ramp, so the local statistic reads 0 inside each gene and 1.0 in the gap and admitted **one** column of 4,258 on the synthetic fused fixture. Deleted from this path only (`call_variants` keeps all four for components): `in_core` / `_core_region`, the terminal-column exclusion, the indel FDR bypass, the 64-column cap. `ε_floor` is the annealing knob and applies as a **floor**, never a replacement — a replacement would set round-1 homopolymer ε to the floor against a 22% measurement and round-3 substitution ε below its own prior. Homopolymer context is measured on the PWM's own columns with gap-winning columns filled by the best base voted there: `cres.frame` writes `-` at a losing insertion column, which cuts the run exactly where the homopolymer null has to judge it. **Run collapse** is exact and is the primary cost control — two adjacent columns share a covered read-set unless some member's span starts or ends between them, so a maximal run with no interior boundary partitions the reads identically; on the 4,000 nt / 400-read synthetic fused fixture that turns 4,058 candidates capped at 512 with `Σkᵢ² = 5.2e7` into 3 representatives at 1,017, and the cap stops binding. Because the collapse is exact, `run_len ≥ 2` means the representative **is already a clique**, and the covariance pass must treat it as one or collapsing would silently delete the alternative-start node. Span endpoints are clustered support-ranked within ±`boundary_tolerance` (default 10) — the same rule `cluster_junctions` applies to intron donors — because 5′ ends jitter by a few nt and 30 reads of one start mode spread over 30 adjacent positions are arithmetically indistinguishable from a ramp.

*`covariance.py`* — written against plain `(candidate index, read index)` arrays only: no `ConsensusResult`, no `MemberSpec`, no ORFs, no edlib, so the clique and assignment claims are *proved* on hand-built inputs rather than asserted through an end-to-end fixture. Retention is `keep[v]` iff some significant edge touches `v`. Co-occurrence is a sparse `Aᵀ·diag(w)·A`, with the pure-coverage × pure-coverage block **never computed**. Four corrections the spec did not anticipate, each forced by measurement: (1) **a degradation ramp's uncovered sets are *nested*, not uncorrelated** — coverage is an interval, so "uncovered at u" and "uncovered at v" are both implied by "ended before min(u,v)", and a 300-read ramp tests at p = 9e-44 across 200 columns. No threshold separates a ramp from a start mode on that statistic, so pure-coverage pairs are excluded from testing rather than thresholded; a collapsed coverage representative is judged instead by a Poisson upper tail on its delimiting boundary mass against a **locally uniform** endpoint null, which is the contrast that actually distinguishes a mode (endpoints piled at one position) from a ramp (endpoints scattered evenly). (2) **The test is two-sided** — depletion is evidence: gene A's columns and gene B's columns describe the same partition from opposite sides, so a one-sided test finds no edge, they become separate signatures, and the state-tuple product re-splits the template along a partition it had already made. (3) **The expected-cell ≥ 5 rule is disabling, not conservative** — it demands `k ≥ √(5n)`, 51 reads of 520, rejecting precisely the low-frequency linked proteoform the design exists to preserve; χ² covers the dense pairs (the exact test is ~51 µs/pair, ~6.7 s per template at the 512-column cap) and an exact hypergeometric covers the sparse ones. (4) **Greedy quasi-cliques must seed with an *edge*, not a node** — at |S| = 1 the growth rule admits any neighbour, so a node-seeded greedy picks a spurious bridge between two real cliques and stalls at size 2, splitting exactly what it was meant to keep apart; seeding at the neighbour sharing the most common neighbours starts inside a dense region (a bridge edge has zero triangles, a clique edge has |C| − 2). Bron–Kerbosch is rejected — exponential on the fused-template hairballs where it would be needed, and *maximal* is the wrong target since one missing edge yields two maximal cliques where the answer is one signature — but kept as a **test oracle** on disjoint unions of cliques. Reads are assigned by likelihood over the columns they *observe*, where an **unobserved column contributes exactly 0** — the direct fix for the 28.1% coverage-class nodes. Since the match term is pattern-independent the argmax reduces to an ε-weighted Hamming distance with `w_c = log((1−ε_c)/ε_c)`, which is the physical content: a substitution column is worth 5.8 nats and a 22% homopolymer column 1.27, so the unreliable column is discounted rather than excluded, and **"matches nothing" is not a case** — exact-row grouping has one, a metric does not.

Three further things measurement forced in `mstep.py`. **Nodes are trimmed to the span their own reads cover**: a child built on the pooled column plan has a column for every position of the parent and the kernel falls back to the template base where nobody voted, so a node whose reads all start 200 nt in emitted the parent's first 200 nt as its own reference — the mechanism behind unbounded reference inflation, and without the trim an alternative-start split produced two nodes of *identical* length. Only the flanks are trimmed; an interior hole means the node spans two disjoint regions and splicing them would fabricate a junction. **Uncovered is a state at *pure*-coverage columns only**: a dual-route column already carries the coverage fact through its block's collapsed representative, so letting it speak again made a read outside a block say "I am not here" once per column of every other block — 85 states per read instead of ~21 on a 12 kb six-gene fused template, past `max_state_per_read` for *every* read, which silently emptied the whole co-occurrence pass. **`plan_columns` gains `terminal_min_support`** (exposed as `min_extension_support`, default 3) because `_covers_junction` enfranchises only reads anchored at that end (191 of 324 members on a real cluster), so two reads could reserve a terminal block that then covaries with itself and spawns a template every round — template *explosion* where the pre-existing failure was template *inflation*. Nodes are emitted by **state-tuple** rather than per signature so `Σ n_reads == template total` (the invariant quant depends on) and two independent signatures give up to four templates rather than two marginals that double-count reads; over-cap tuples go to the nearest survivor by the same ε-weighted metric, which is the modal-absorption deletion applied one level up. `refine_template` returns `disagreement_stats(pooled)` plus the covariance counters on the major node, so the round loop can refit ε from round *r* and pass it in as round *r+1*'s prior — which sidesteps the components path's hardest part entirely: there a refit is retro-applied via `reclassify_variants` and then needs `_reconcile_haplotypes_after_reclassification` to undo demoted columns, and that reconciliation explicitly cannot handle *promotions*.


**Review-driven corrections to M-step v2 (2026-09-15).** A second external review found eight defects, all reproduced and all with regression tests. Three were crashes or fabrication: the length-filter report called a logger that only exists under `verbose`/`progress_cb`, so **every quiet run that actually dropped a window raised `TypeError`**; a child sharing a pooled column plan emitted one `N` per column of a block some *other* population created (`AACCGG` → `AACNNNCGG`), because the unresolved-N rule is about a base the **template** carries and an insertion column carries none — fixing it also corrected child reference lengths on the synthetic fused fixture from 4120/4139/4139 to the true 2000/1800/1800; and `_child_position` returned a kept column's *inclusive* consensus index for what callers use as an *exclusive* bound, clamping `n_columns` to `n_columns − 1` at the template's own end, so a seed ORF ending there came back one base short and the support gate truncated inside the interval it is explicitly told to treat as certified (a 126 nt seed reported `orf_end=123`). `_consensus_offset` counts the consensus bases preceding a PWM column — one exact answer for both ends, since an inclusive start and an exclusive end both want that count.

The two structural ones. **Pattern seeding was exact-row matching**, which reintroduces the "matches nothing" case the assignment metric exists to avoid, one level up: `P(clean row) = (1−ε)^S` is 79% at 24 columns and ~0 at a few hundred. Measured on a 100-major / 40-minor fixture over 24 linked columns it was unstable in *both* directions — one error per read shattered the major population into six spurious 5–7 read nodes, two errors found no qualifying row and emitted a single 140-read node. No threshold fixes that, and `a_min = 3` was only its visible edge. Patterns are now grown by the same ε-weighted metric that assigns reads: start from the weighted per-column majority, seed each new one from the **worst-explained read**, re-fit, and keep it only if the likelihood gain clears a **BIC penalty** of `(S + 1)·ln(N)` nats. That penalty is what separates the two failures — a junk pattern capturing six reads that each save one column gains ~35 nats against ~123 and is refused, while a real 40-read minority differing at 22 columns gains ~5,100 and is kept, and so is a *3-read* minority differing at 24, which the old read floor could not express. `pattern_penalty` scales it, so the round loop can anneal how readily a template splits. And **the numerator, the marginals and the denominator described different populations**: `_cooccurrence` censored reads by their state count while the observation tables kept them, so an exactly independent pair came back at `p = 4e-88` through the depletion tail. Censoring a read by how many states it carries is censoring on the thing being measured, so the control is replaced rather than made consistent — `max_cooccurrence_budget` drops the lowest-**effect columns** until the projected `Σkᵢ²` fits (the ranking `max_candidate_columns` already uses), and dropped columns are excluded from pair enumeration too, since admitting them would read `n11 = 0` and fire the same tail.

Three smaller ones: an internal `N` inside a read's span was read as absence, so at a coverage column a basecall manufactured evidence for a coverage split (an in-span ambiguity is now presence; an in-span ambiguity at an *allelic* column still reads as the major allele, a conservative approximation that keeps the interval-dominance observation counts exact); the single-index-part guard bounded the reference but not the **indexing configuration**, so a lowered `-I` still built a multi-part index and counted a read's mass once per part (measured: 2 reads → 2 assignments at 16G, 4 at 1K), and `-I` is now validated against the template total; and `allow_antisense` had **no correct implementation** — PAF reports `q_start` on the forward query while `cg:Z` describes the reverse complement, so a hit supporting `GGGG` voted `CCCC` into the PWM — and is removed rather than left as a silently wrong opt-in.

**Known performance work, deliberately deferred.** The same review measured three allocation hot spots. The signature scorer is fixed (chunked over reads; the natural form allocates a dense `(M, K)` float64 mismatch product — 78 MiB *per pattern per iteration* at 20,000 reads × 512 columns). Two remain and are follow-ups, not merge blockers: `frame_consensus` holds per-base projections, scatter indices, weights and their concatenation simultaneously (+94.8 MiB for 1,000 × 2 kb reads, +284 MiB for 3,000), and `assign_reads` accumulates every assignment and coverage row in Python lists until one final Arrow conversion (+70.2 MiB / 3.16 s for a 20,000-read × 10-template fixture, excluding alignment). Both want the same treatment the resolve stage already has — bounded Arrow batches out, reused compact buffers in.

**Input length filter.** `load_demux_windows(demux_dir, *, max_window_length=None)` drops oversized windows at the corpus boundary — before `dereplicate`, so uniq abundances are right for free — and returns `(reads, stats)` with `n_input` / `n_dropped_long` / `max_input_length`. It belongs there and not at seeding because three consumers read the corpus and filtering at seeding removes the read from only one of them: it still wins a banded hit, still lands on a template, and still contributes its unaligned flank to `plan_columns` as an extension event, so a pair of 40 kb reads reserves a 40 kb terminal block on someone else's template. Oversized windows are **dropped, never trimmed** — a 361,908 nt "cDNA" is a concatemer, and truncating it to 15 kb manufactures a read that was never sequenced. Measured: 2,220 windows >15 kb (0.024% of reads), 929 >25 kb; round 1's maximum template length equals the input maximum, and removing them eliminates 901 round-1 giants.

**Review-driven corrections (2026-09-08).** An external review of the ORF-EM stages found eleven defects, ten with regression tests that fail on the parent commit (`tests/test_denovo_review_regressions.py`). The theme is one value computed in one coordinate space or over one population and consumed as if it belonged to another. Five were P1: (1) `run_estep` was **dead on arrival** — `minimap2_stream` yields byte chunks off a live pipe and has no `.read()`, which `iter_paf_batches` called unconditionally; every existing test used `BytesIO` and so missed the only interface that matters in production. (2) The M-step's haplotype gate keyed "is this an indel" off the **minor** allele, but on a minority insertion the *major* allele is the gap — reinstating the insertion/deletion asymmetry the planned column space exists to remove, one layer up. (3) Declared variants were copied from the pooled consensus into every child, so the majority node declared a column it does not contain; children are now built on the **pooled column plan** and each maps the shared PWM columns into its own consensus, dropping the ones it has no base for (a minority insertion exists for the node carrying it and nowhere else). (4) The support gate had only a 3' end, so an upstream ATG could extend a protein through uncovered flank while sharing the seed's stop. (5) The seed boundary was not transformed per child — deleting 30 upstream bases moves an ORF end from 336 to 306, and reusing the parent's number certified ten unsupported residues; `seed_orf` now arrives in **template** coordinates and is resolved through the shared plan into each child.

P2: a read ending *exactly* at an insertion junction was casting a gap vote there, so ten reads that stopped short outvoted six that spanned it and carried the base — an interior junction now requires the alignment to **span** it, while terminal junctions keep their anchored semantics. A dropped terminal column takes its `consensus_pos` from the last kept column, so a 3' extension block anchored inside the core and a 75/25 length mixture could define haplotypes; **column provenance** settles it, and note the criterion cannot be per-column base coverage since an interior insertion column is low-base-coverage by construction. Fractional mass was split across alignment *records*, so a read placing twice on one template claimed two thirds of its own mass for it (now one placement per template, best-scoring; the coverage table is likewise one row per read×template). A terminal clip and an insertion op at the same junction are the same junction, and a dict over them dropped one, turning four unanimous 5' bases into two. Reverse-strand PAF clipping was reconstructed forward — PAF reports `q_start`/`q_end` on the forward query while a SAM CIGAR is alignment-oriented, so on `-` the clips swap. `orf_identity` measured the whole alignment, scoring a read that matches the CDS perfectly but disagrees across both UTRs at 0.4 instead of 1.0.

One reported item did **not** reproduce: an abundant suffix ORF suppressing valid folding comparisons — with a 20-read suffix anchor the two longer ORFs still folded together. The structural concern is real (anchor-star candidates plus post-hoc classification can leave a pair uncompared), so `fold_orfs` gains a second verify pass over the group *representatives*, which costs a few thousand sequences rather than a few hundred thousand and is the same rule-1 merge the round loop will apply to consensus ORFs. Also: `member_alleles` no longer re-parses every CIGAR — `frame_consensus` caches the projections it already built for the scatter, which are all live during it regardless, so peak memory is unchanged.

**Consensus kernel: a pre-planned PWM column space (`denovo/consensus.py::frame_consensus`).** The v1 kernel projected members onto the centroid and **dropped** every member insertion, so the consensus could never be longer than the centroid and a deletion error *in the centroid* was unrepairable no matter how many members carried the base — 120 reads carrying a base could not put it back into a centroid that lacked it, and the result depended on which read became the frame. Measured cost on the shipped path: ~25% frameshifted consensuses at single-read-centroid depth vs 6% for POA (ledger #17).

The fix is **not** to vote insertions in. The obvious repair — build the PWM, find junctions where a majority inserts, splice them in, re-align, iterate — was built first and is wrong for this pipeline: it decides an insertion's fate by majority *before* the variant caller and haplotype resolver ever see it, so a 25%-frequency insertion is voted out of existence and can never define a node, while the identical minority *deletion* resolves fine (it is just a gap vote in a column that already exists). Measured on a 75/25 split: the deletion direction gave 2 nodes (75/25, alleles `A`/`-`), the insertion direction gave 1 node of 100. That asymmetry turns on nothing but which direction the seed read happens to differ from its own variants — arbitrary in the worst way for a pipeline whose product is proteoform nodes.

So the column space is **planned in advance from the members' own CIGARs** (`plan_columns`): wherever a supported group carries an insertion, a block of columns is reserved before the template column it precedes, and every member covering that junction votes there — a base if it inserts, a **gap** if it does not. Terminal blocks (unaligned 5'/3' flanks) are the same mechanism, so "end extension" and "insertion folding" are one thing. The ordinary per-column argmax then decides what reaches the consensus and the resolver decides what defines a haplotype. Post-fix both directions give 2 nodes at 75/25 with complementary alleles. It is also strictly less machinery — **one pass, no re-alignment, no iteration**, no insertion-specific thresholds beyond the support floor. `min_insertion_support` (default 2 members) sizes each block: a singleton insertion reserves nothing, so a chimeric read cannot widen a template it does not belong to, and `L_j` needs no cap because a read carrying sequence no template explains should fail the E-step's band and seed its own template. A minority insertion's unkept columns cost memory, not correctness.

**Three coordinate systems** — template (`T`, the string handed in) → frame (`F ≥ T`, what `pwm`/`winner` index) → consensus (`C ≤ F`, gap-winning columns removed) — with `template_of_frame` / `frame_of_cons` / `cons_of_frame` / `column_kind` as the public maps. Use `frame_of_consensus()` / `consensus_of_frame()` rather than open-coding: `np.flatnonzero(winner < 4)` and `winner != 4` disagree on the unresolved-`N` column (`_AMBIG=5`), which the consensus deliberately **keeps**, so the open-coded form in `pipeline.py` shifted every variant downstream of the first `N` (fixed). `FrameAlignment` carries **template** coordinates (`template_start`/`template_end`) and walking one against the expanded space is the same bug class — `member_alleles(cres, columns)` is the sanctioned reader, resolving both spaces and returning `0-3` base / `4` gap / `-1` uncovered.

**`variants.py`: testability is decoupled from consensus membership.** An insertion column is majority-gap by construction, and `cand = keep & …` (where `keep = winner != 4`) skipped exactly those columns — 0 variants called on a clean 25% minority. Candidacy is now depth + a real minor allele; `in_core` still handles the terminal ramps `keep` was partly proxying for. An indel is now "either allele is a gap" (on an insertion column the *major* is the gap, so keying off the minor scored a length change against the substitution null), and `call_variants` reports a 13th field, `pwm_column` — the address in the PWM's own space, since an insertion column has no consensus position and its `consensus_pos` is the preceding kept column, an anchor rather than an address. Callers strip it before writing `CLUSTER_VARIANT_TABLE`.

**The frame's self-vote is 0** in the EM path and the centroid joins the PWM as an ordinary member with an identity CIGAR: the seed read is also an assigned member so a self-vote double-counts it, in later rounds the frame is a consensus with no reads at all, and the PWM column sums must stay raw read multiplicity because `variants.py` uses them as its binomial `n`. `centroid_consensus(centroid, weight, members)` remains as a **bit-identical** v1 shim (single pass, no planning, centroid self-votes) — verified over 200 randomized trials across both edlib orientations. Measured on the 120-transcript synthetic panel at `--identity 0.96`: exact consensuses 4 → 17, median edit distance to truth 6 → 3, mean 6.20 → 3.57, **faster than the fold-off path** (2.8 s vs 3.2 s). `--no-fold-insertions` restores v1 behaviour. `_cigar.py::parse_cigar` is now **strict** — it silently returned `[(90,'M')]` for `"10S90M"`, which would shift a projected member by the clip length; `parse_cigar_clipped` handles terminal clips and `indel_runs` counts indel *events* (what the frameshift-pair fold rule needs).

**Diagnostic-report system (`transcriptome/{align,cluster}/diagnostics.py` + `transcriptome/_render.py`).** Each pipeline stage emits a markdown report with embedded SVG figures under `<output>/diagnostics/`. Metrics are pure functions over the existing parquet outputs (no extra pipeline state); reports are auto-emitted at the end of `transcriptome align` / `transcriptome cluster` (opt out with `--no-report`) and can be regenerated read-only via `constellation transcriptome diagnose --align-dir DIR [--cluster-dir DIR] [--reference HANDLE] [--organism-profile PROFILE]`.

- **Align report** (`<align-dir>/diagnostics/report.md`): run parameters table + minimap2 resolved-args, intron length distribution colored by motif, splice motif composition (GT-AG / GC-AG / AT-AC / other by both cluster count and read count), annotated junction agreement by supporting-read tier, alignment complexity (blocks per primary), MAPQ distribution, **multi-gene alignment counts** (the fusion smoking gun — per-alignment count of overlapping annotated genes, flagged at >2% multi-gene).
- **Cluster report** (`<cluster-dir>/diagnostics/report.md`): run parameters, cluster size distribution (singleton-fraction + top-cluster flags), cluster span vs annotated gene length, **multi-gene cluster overlap** (same fusion smoking gun on the cluster stage), drift filter statistics, layer-0 dereplication ratio, intron-chain complexity (joins back to upstream align dir to count representative-alignment blocks; flags mega intronless buckets), consensus quality (per-member match_rate / indel_rate).

Flag thresholds bubble into a top-of-report **FLAGS** section so a reader skimming the report sees red flags first. Per-metric failures are caught by the orchestrator's `_safe` wrapper and render as a stub note — a single broken metric never breaks the whole report, and report-generation failures during the auto-emit never break a successful pipeline run (the CLI logs a warning + a re-run hint pointing at `constellation transcriptome diagnose`).

Figures: SVG via matplotlib Agg backend (lazy-imported inside `_render.save_svg_figure`). Renders inline in GitHub / VSCode markdown previews; small file size for the chart types we emit (histograms, bar charts, small overlays). Flag thresholds for the intron-length section are profile-aware (`_PROFILE_MAX_BIOLOGICAL_INTRON_BP`: 50 kb / 100 kb / 1 Mb for compact / intermediate / animal). Adding a new metric: write a pure function `section_<name>(table, *, figures_dir, ...) -> ReportSection`, register it in the per-stage orchestrator's `sections.append(_safe(...))` chain; the FLAGS hoist is automatic. The standalone `diagnose` verb picks the new metric up for free.

## Conventions (sequencing layer)

- **Sequencing containers do NOT mirror the massspec Library/Quant/Search trio.** Sequencing's natural shape is `acquisitions + samples + reads + alignments + (genome reference, annotation, transcript reference) + assembly + quant + annotation tools + genetic_tools`. The MS theoretical/empirical split doesn't transfer because for de novo work the "library" *is* the experimental output. The reference layer is **split into three sibling Library-shaped containers** because real-world references are heterogeneous: `GenomeReference` (`CONTIG_TABLE` + `SEQUENCE_TABLE`), `Annotation` (`FEATURE_TABLE`, FK into a `GenomeReference`), `TranscriptReference` (`TRANSCRIPT_TABLE`; populated either from a paired GenomeReference + Annotation via `TranscriptReference.from_annotation` or from a standalone transcript FASTA when no genome exists). Each ships PK/FK closure + ParquetDir native form + Reader/Writer Protocols. `GeneticTools` is the cRAP-equivalent for genomics — a curated bundle of common cloning / engineering parts (AbR / FPs / tags / promoters / common enzymes / vector backbones) at `constellation/data/genetic_tools.json`. `Assembly` is its own container with provenance Reference doesn't need (read-coverage, polishing rounds, scaffolding edges) and `Assembly.to_genome_reference()` lifts a finalized assembly into the same `GenomeReference` shape so external-ref and de-novo-ref workflows share downstream code; companion Annotations build separately from BUSCO / RepeatMasker / telomere passes. `Quant` keys per-feature counts/coverage/TPM on `(feature_id, sample_id, engine, feature_origin)` — multi-tag, see below. `Alignments` is its peer container (per-acquisition, FK to `GenomeReference`). No `Search` analog — alignments are observations, not detection scores.

- **`feature_quant` is multi-tag, not strict-precedence.** `FEATURE_QUANT` carries a `feature_origin` column with vocabulary `'gene_id'` | `'transcript_id'` | `'cluster_id'` | `'genetic_tool'` | `'protein_uniref'` | `'protein_hash'` (frozen set in `sequencing.schemas.quant.FEATURE_ORIGIN_VOCAB`). `feature_id` is unique within a `feature_origin` partition; sums within a partition are valid counts; **never sum across partitions** (different statistical models of "what a feature measures"). The transcriptome S1 naive-ORF output projects into FEATURE_QUANT under `feature_origin='protein_hash'` via `transcriptome.quant.to_feature_quant`; future genome-aligned gene counts use `'gene_id'`; transcriptome-mode EM lands `'transcript_id'`; mmseqs2 hits land `'genetic_tool'` or `'protein_uniref'`.

- **External-format readers are hand-rolled, stdlib only.** `readers/fastx.py::read_fasta_genome` / `read_fasta_transcriptome` / `read_fasta_genetic_tools`, `readers/gff.py::read_gff3` / `write_gff3`, and `readers/bed.py::read_bed` are pure-Python streaming parsers (gzip-aware via stdlib). No `pyranges`, no `gffutils`, no pandas. Reasoning: pyranges1 pulls pandas + a gtfreader sub-dep + a Rust backend; pysam.FastaFile only earns its keep on huge genomes that need `.fai`-indexed random contig access (we do full one-pass reads). Same precedent as `readers/sam_bam.py` — pysam stays scoped to where its CIGAR / virtual-offsets / sorting machinery is genuinely irreplaceable. Coordinates are 0-based half-open internally; GFF3 (1-based inclusive) and BED (already 0-based half-open) convert at the reader boundary.
- **`Samples` is first-class in sequencing, not derived.** A sample = `(acquisition_ids, barcode_id?)` resolved via the M:N `SAMPLE_ACQUISITION_EDGE` table. Single-sample multi-flowcell (genomic ultra-HMW; barcode null) and multi-sample single-flowcell (multiplexed transcriptomic; M barcodes) and mixed designs all use the same schema — no bifurcation by experiment type.
- **Generic `ragged_trace_1d` schema covers POD5 + future MS scan blobs.** Variable-length 1D-array-per-row with rich row-level metadata earns a slot in `core.io.schemas` (≥2 modalities). POD5 reads are 1k-5M+ samples each (~10¹³ rows if flattened to `Trace1D`); MS scans are 10⁴-10⁵ peaks each. The factory takes a value dtype + optional explicit-x column + per-row extras: POD5's `RAW_SIGNAL_TABLE` instantiates with `value_dtype=int16, value_name='signal'`, future massspec scans with `value_dtype=float64, value_name='intensity', x_name='mz'`. `ragged_to_tensors` projects the ragged columns to per-row torch tensors (each row may have a different length — caller pads / batches).
- **Demux output is segment-row-shaped, not read-row-shaped.** `READ_SEGMENT_TABLE` carries one row per *located segment* (adapter / polyA / barcode / transcript / UMI) — chimeric / concatemer reads (very common in nanopore) emerge as multiple segment-runs per read without any chimera-aware special casing. Demux logic operates on `LibraryDesign(layout: tuple[Segment, ...])` composed of `AdapterSlot` / `BarcodeSlot` / `PolyASlot` / `UMISlot` / `TranscriptSlot`; new ONT/SMARTer-derived chemistries land as new designs without code changes. `Adapter` and `Barcode` are independent registry-grade objects (kits share adapters across products). `READ_DEMUX_TABLE` is the derived view: one row per resolved transcript window with `sample_id` assigned and `is_chimera` flagged.
- **Sequencing demux uses segmented edlib over Dorado's full-primer Smith-Waterman.** Three-step algorithm (lifted from NanoporeAnalysis): (1) anchor on polyA via error-tolerant 'AAAA' edit-distance scan, (2) locate 3' PCR adapter on polyA-side; score the gap region against barcode panel, (3) locate 5' adapter and isolate transcript window. Beats Dorado's built-in demux because high homopolymer error in nanopore A-runs (lab measurement: mean A=26 against expected A=20) distorts SW scoring of the full primer enough to misassign barcodes; segmenting on polyA first and scoring only the discriminating region sidesteps this.
- **`Scorer` Protocol — pluggable per-segment scoring; `HardThresholdScorer` is production.** `transcriptome.scoring.Scorer` is the seam between hard-threshold and probabilistic scoring of segments (polyA / 5' adapter / 3' adapter / barcode panel). The orchestrator (`transcriptome.demux.locate_segments`) calls `Scorer` methods uniformly — swapping modes is a one-line change at the CLI / API surface, not a fork in the demux algorithm. `BarcodeVerdict.delta_edit_distance` is the gap between the best and second-best matches across the FULL panel (not just within-budget candidates), so `READ_SEGMENT_TABLE.score_delta` is directly useful as a diagnostic — a 0-vs-1 best-second gap is much weaker evidence than a 0-vs-6 gap even though both look like "Complete" matches under the hard threshold. **`ProbabilisticScorer` is deferred indefinitely** per the scoring-domain rule below; the seam stays in place at zero cost so a future basecaller emitting trustworthy posteriors can drop in without re-architecting demux.

- **Scoring-domain rule: don't dissect basecaller artifacts in the demux scorer.** `HardThresholdScorer` matches NanoporeAnalysis `_fixed1` semantics with three deliberate accuracy improvements over the upstream baseline and is the production scorer. The originally-planned `ProbabilisticScorer` (S2) was meant to fit calibrated `Parametric` distributions over polyA length / adapter edit distance / barcode panel scores, with priors learned from the empirical distributions in `analyze-demux-statistics.py`. **We deferred this work after the polyA-by-barcode diagnostic showed that per-barcode polyA-length systematics are dominant and motor-coupled** — see `data/sequencing/cdna_wilburn_v1.json::calibration_notes` (BC06 example: TAT-repeat structure interacts with the motor protein during the polyA dwell, biasing the basecaller's dwell-time → A-count conversion). Calibrating a probabilistic demux scorer to the basecaller's per-barcode artifacts would be curve-fitting to a black box rather than recovering signal. The principled path lives one layer earlier: (a) **signal-level demux** working on the raw POD5 squiggle directly (change-point detection on dwell-time series, not sequence similarity on basecalled output — same domain as `signal.models.physical` for direct-RNA modifications), or (b) **better basecaller training** with constellation supplying the trustworthy-ground-truth fixtures (synthetic-read corpus + lab-measured systematics) a training run needs. The `Scorer` Protocol seam stays — drop-in for whichever path matures first — but no `Parametric` calibration work happens against current Dorado output.

- **The simulator + stats infrastructure is a diagnostic tool, not a calibration substrate.** `transcriptome.simulator` and `scripts/analyze-demux-statistics.py` were originally designed to feed S2's prior calibration. After the scoring-domain pivot above, they keep their value — for spotting basecaller drift across Dorado versions (re-run the stats script on a new Dorado release; if BC06's polyA mean shifts, the basecaller's homopolymer model changed), regression-testing `Scorer` implementations against the synthetic ground truth, and characterising per-(library design × basecaller) systematics. They are NOT a substrate for fitting empirical priors that pretend to recover ground truth from current Dorado output.
- **HardThresholdScorer corrects three NanoporeAnalysis bugs deliberately.** (1) Filter edlib's `editDistance=-1` no-match sentinel before picking a winning barcode (NanoporeAnalysis's filter checks `is not None`, which leaks `-1`s and assigns no-match reads to whichever barcode is first in dict-iteration order). (2) Short-circuit on empty `ref` strings in `locate_substring` — edlib on an empty subject returns `editDistance=len(query)` with `locations=[(None, -1)]`, which NanoporeAnalysis treats as a "match" and ends up assigning bogus 16-edit-distance "matches" against empty putative_umi regions. (3) Pick the non-Unknown orientation cleanly when exactly one orientation classifies as Unknown — NanoporeAnalysis's `cDNA[1] == 'Unknown'` literal-string check fails when reverse is `'Unknown Fragment'` (not just `'Unknown'`) and silently throws away forward's real annotation. All three are documented in code where the divergence happens; constellation's behavior is strictly more accurate than the upstream baseline.
- **PolyA-barcode boundary ambiguity is a scoring concept, not a panel-data property.** When a barcode's RC begins with 'A' (BC05/06/11/12 in `cdna_wilburn_v1`), polyA detection greedily absorbs the leading A — the barcode matches the panel at ed=1 instead of ed=0. The leading A is information-theoretically null under hard-mode scoring (no upper bound on polyA length means no signal in length variation). The Pichia-flowcell diagnostic (calibration_notes in `cdna_wilburn_v1.json`) checked whether stratifying polyA length by leading-A-RC-class recovers a clean bimodal structure that a probabilistic scorer could exploit — answer was **no** (means within ~0.1 nt of each other; per-barcode systematics like BC06's TAT-repeat motor effect are larger and unrelated to leading-A class). The boundary-absorption hypothesis is documented but does NOT appear to be the dominant source of polyA-length variation. Per the scoring-domain rule above, never strip from the panel + never trim at scorer setup — the per-barcode polyA-length empirical distribution stays intact as a Dorado-behaviour diagnostic, and downstream consumers that care about boundary ambiguity address it at the basecaller level (signal-domain demux), not the demux scorer.
- **S1 stage parallelism: per-worker file chunks, fused ingest+demux, partitioned-parquet shards.** `sequencing.parallel.run_batched` is the generic batch executor: each worker writes its own `<output>/<key>/part-NNNNN.parquet` shard directly (no Arrow tables pickled back to the parent), `_SUCCESS` markers gate stage-level resume, missing shards inside an unfinished stage trigger shard-level partial recovery. `transcriptome.stages.run_demux_pipeline` orchestrates `_plan_chunks` (parent-only; cheap chunk-spec computation) → `run_fused_demux_stage` (N parallel workers each do ingest + demux + ORF) → `resolve` (sequential aggregation). For BAM, the planner does a fast no-decode pysam scan (`_bam_record_chunks` in `readers/sam_bam.py`) recording record-boundary virtual offsets every `chunk_size` primary records; for SAM, byte-range chunks split at newlines via the worker-side handshake protocol (each worker discards a partial first line if not at file start, then reads complete lines until past `byte_end`). Each worker opens its own pysam handle on the source file, so ingest is fully N-way parallel — no parent-serial bottleneck. Replaces NanoporeAnalysis transcriptome_nf (Nextflow per-batch fan-out → physical SAM shards on disk) with `--threads N` + `--batch-size` + `--resume` CLI flags. Worker function (`transcriptome.stages._fused_chunk_worker`) lives at module top level so `ProcessPoolExecutor` can pickle it; designs are loaded by NAME inside workers (cheap JSON read; cached) rather than pickled across the IPC boundary. Each worker emits 4 shards: `reads`, `read_segments`, `read_demux`, `orfs` — the `reads` dataset is partitioned (one parquet per worker), queryable via `pa.dataset.dataset(reads/)`.
- **Progress reporting is a Protocol, not stdout calls.** `core.progress.ProgressCallback` accepts `ProgressEvent` (kind: `stage_start` / `stage_progress` / `stage_done`, plus `stage`, `completed`, `total`, `message`, free-form `payload`). CLI binds `StreamProgress` (one line per event to stderr) under `--progress`; future GUI binds the same Protocol to a Qt signal or websocket. The core verbs in `parallel.run_batched` and `transcriptome.stages` take `progress_cb: ProgressCallback | None` and emit at well-known points without caring how the host renders them. The Protocol lives in `core/` rather than `sequencing/` so massspec verbs (the Thermo converter, future mzML / Bruker / Sciex readers) can share it — domain modules never cross-import.

- **Resolve-stage pitfalls observed at mouse / PromethION scale.** Four distinct bottleneck classes were learned the hard way during the resolve-stage rewrite — all single-thread, all looked innocuous in the toy-scale tests, all were measured in hours-to-days of wall time before the fix. Avoid these patterns in any future resolve-stage code:
  1. **Calling a method that does work-per-call inside a hot row loop.** `GenomeReference.sequence_of(contig_id)` does a `ChunkedArray.to_pylist()` over the contig table and then `.as_py()` to decode the entire chromosome sequence (~200 MB for mouse chr1) into a fresh Python str. Innocuous at "tens of thousands of junctions" — catastrophic at 1M+ junctions (the actual mouse number). Always prefetch per-contig values into a dict before any junction-row loop. Same principle applies to any uncached property of `Annotation`, `TranscriptReference`, etc.
  2. **One-sided `searchsorted` bounds on interval-overlap joins.** Both halves of the half-open overlap predicate (`exon_start < block_end` AND `exon_end > block_start`) must contribute to the candidate slice. Sorting by `exon_start` gives only the upper bound; the lower bound needs `searchsorted` against `cummax(exon_end_in_start_sorted_order)` — the prefix-max is monotonic, so binary-searchable, and prunes "exons that have already ended" from the candidate range. Without it, `total = sum(counts) ≈ n_blocks × n_exons` and the intermediate explodes.
  3. **`O(N×M)` Python set scans inside per-partition loops.** `[p for p in cuts_set if iv_start < p < iv_end]` repeated across thousands of intervals × dozens of partitions is the same algorithmic mistake as #2 dressed differently. Sort the set once per partition; `bisect.bisect_right` + `bisect.bisect_left` to slice the interior range.
  4. **String columns in wide-table sort + combine_chunks.** Arrow's string-array `combine_chunks` offsets-rewrite is partially single-threaded; at 1.4B+ rows of `read_id` it pins one core for hours. Project to numeric-only columns BEFORE the sort, attach strings via a final small join on the post-aggregation table. Same caution applies to materialising large datasets via `pa.dataset.to_table()` — pass `columns=[...]` to project at scan time and drop the bulky strings (`cigar_string`, `read_group`, etc.) the resolve stage doesn't need. `compute_exon_psi`'s `role` column is emitted as `int8 role_id` for the same reason: at 419M aln_exon_role rows, "spanning"/"partial" strings cost ~4 GB vs ~400 MB for the int8 encoding.

  A related streaming pattern that's now standard: `assign_blocks_to_exons` and `build_pileup` are streaming Parquet writers when given `output_path`; `compute_exon_psi` consumes `block_assignments` from disk as a `pa.dataset` and stream-extracts distinct overlap pairs; the join-aggregate step inside `compute_exon_psi` uses `_join_aggregate_streaming` to slice `aln_exon_role` in zero-copy chunks rather than materialise the full 419M-row left-join. The combined effect on the production mouse run: resolve stage went from 12+ hours hung (with ~95 GB peak before OOM was even reachable) to ~7-8 min within the 19.5-min end-to-end target, with peak RSS bounded by the alignments + blocks + read_demux materialisation budget.
- **`align/` modules named by verb, not backend.** `pairwise_align(query, ref, *, backend='edlib'|'parasail')`, `map_reads(reads, reference, *, backend='mappy'|'minimap2')`, `locate_substring(query, ref, *, max_distance)`. Backend choice is a kwarg, not visible at the import level — keeps demux / polish / scaffold callers clean and lets us swap implementations without touching call sites.
- **`DoradoModel` parses lab shorthand.** `DoradoModel.parse("sup@v5.0+5mC,5hmC")` → `DoradoModel(family='sup', version='v5.0', chemistry='dna_r10.4.1_e8.2', mods=('5mC', '5hmC'))`. Default chemistry is DNA R10.4.1; explicit chemistry prefix (`"rna004_130bps_sup@v5.0.0+m6A_DRACH"`) handles direct-RNA. `model_name()` renders to Dorado's canonical on-disk model directory name; `modified_bases_arg()` formats for the `--modified-bases` CLI flag.
- **`DoradoRunner` returns `RunHandle`, never blocks.** Single-flow-cell sup-model basecalling takes 3-4 days on an A100 — long enough that blocking the Python session is wrong. `RunHandle` exposes `wait()` / `poll()` / `tail_progress()` / `cancel()`, and `RunHandle.attach(pid_file)` rebinds to a previously-detached run from a different Python session (so `constellation basecall --follow` can monitor a job started days earlier).
- **Pure-functional first; `Project` is the orchestrator on top.** Verbs like `bam_dir_to_assembly(bam_paths)` work standalone with no project context. `Project.open(root)` reads a `manifest.toml`, knows the standard layout (`pod5/ → bam/ → assembly/ → annotation/ → transcriptome/`), and is the *only* layer that mutates filesystem state — same pattern as `Library` / `save_library`. Labs that produce BAMs externally and just want the analysis layer skip the Project entirely.
- **Cross-modality workflows live as top-level scripts (one workflow today).** `constellation/transcriptome_to_proteome.py` is the only such workflow today, so it lives at top-level per the "≥2 workflows before a folder" rule. When a second cross-modality pipeline lands (genome → spectral library, structure → spectral prediction), they co-locate into a dedicated subpackage; name TBD (`bridges/` and `pipelines/` are ruled out — candidates: `asterism/`, `confluence/`, `weft/`, `synthesis/`, `composer/`, `lattice/` — defer until two workflows exist to compare).
