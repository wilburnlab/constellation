# CLAUDE.md — `constellation.massspec`

This file extends the project-wide rules in [../../CLAUDE.md](../../CLAUDE.md). Read that first; chemistry / ProForma / cleavage rules live in [../core/CLAUDE.md](../core/CLAUDE.md).

`massspec/` is the mass-spectrometry domain module. It absorbs Cartographer (the lab's MS proteomics package — first port target) and surfaces Constellation's HUPO-PSI compliance commitments. Layout: a theoretical/empirical/scoring sibling trio (`library/` + `quant/` + `search/`) sharing per-acquisition provenance (`acquisitions/`), peptide-level chemistry (`peptide/`), HUPO-PSI annotations (`annotation/`), cross-tier file-format adapters (`io/`), and per-model tokenizers (`tokenize/`). Beside them sit raw-instrument readers (`readers/` — Thermo `.raw` shipped; mzML, Bruker `.d`, mzPeak land when each reader ships), MS2 spectrum-level operations (`spectra/`), and the ion-count model (`counter/`). One module, `massspec/cli.py`, holds every `constellation massspec` verb (see "CLI surface" below).

**Counter and the transcriptome→proteome pipeline are both due for major revision.** How they connect to the rest of `massspec` today, how EncyclopeDIA is run inside and outside the pipeline, and the defects found and deliberately left unfixed are recorded in [../../docs/plans/massspec-pre-revision-review.md](../../docs/plans/massspec-pre-revision-review.md) (snapshot of 2026-10-10). Read it before changing either.

| `constellation.massspec.counter` | Physically-grounded Bayesian ion-count model ("Counter") — estimates the latent integrated ion count `N_total` (and elution flux `N(t)`) of a peptide species from the joint m/z + intensity likelihood of its observed ions, as a *score* decoupled from RT windowing. **PR-1 (this stream):** `Progenitor(Distribution)` (one species — `HyperEMGPeak` flux × charge partition `softmax(−E_z)` × isotope fractions `p_k` (theoretical log-weights + a **learnable per-isotope correction**, M+0 reference — captures the real high-res ¹⁵N/¹³C convolution effect on M+1/M+2 that scales with the N/C ratio), per-peptide `ν_I`/`c_mz`, shared-by-reference `GlobalCalibration`) + `Panel` (additive joint score over a fixed candidate set + background, soft intensity-weighted attribution `γ_q=I_pred_q/ΣI_pred` for the m/z mixture + Poisson-tail censored term for non-observations); `channels` — **PR-3 reformulated the intensity term to a count-native complete left-censored-Poisson likelihood**: observed channels score `log Poisson(N_obs|λ)` on the recovered count `N_obs=I·τ/α` (`λ=N_count`; Var=λ natively, retiring the Eq.16 multinomial `p(1−p)` variance, which was inconsistent with the marginal-Poisson generative process) and unobserved channels the complementary tail `log P(count<floor|λ)=log gammaincc(floor,λ)` (off-by-one-corrected) — the two partition the same Poisson over disjoint events, the exact bias-free treatment of the detection edge (do NOT also divide observed by `P(count≥floor)` — that conditional framing on top of the censored term double-counts detection and collapses N). The legacy Eq.16 Student-t intensity term is retained for high-N ablation. m/z Student-t with `σ²=c_mz/N_k^{α_mz}` unchanged; `GlobalCalibration` (gain `α(z)` switch `linear`(default)/`linear_origin`/`per_z`, per-isotope `d_mz_k` Da→ppm, global `α_mz`/`ν_mz`, resolution `ρ_R` on the intensity variance); `estimate_n` (PR-2): data-seeded DE+LBFGS-polish MAP warm-start (calibration frozen), then `inference="vb"` (default) — variational credible intervals on `N_total` via a `MeanFieldGuide` over N+peak-shape + `AdamOptimizer` (with a non-finite-gradient skip-guard so an extreme MC draw can't poison the run) + composable priors (`priors.make_log_prior`: RT-seed Gaussian on `μ` = seed-as-prior-not-window, an η-toward-MAP prior taming the HyperEMG η degeneracy, an opt-in toward-theoretical isotope-offset prior) — or `inference="map"` (Laplace CI over the N+shape block). VB CIs are well-calibrated at practical ion counts; the count-native likelihood (above) also corrects the former detection-edge upward bias (MAP recovery at 1e4 ions improved from +30–44% to ≈+4%, CI coverage restored ~4/4 across 5e3–3e5). **`StagedCalibration`** (PR-3) fits a shared `GlobalCalibration` + per-peptide params across a set of calibrant peptides by freeze/thaw stages — `per_peptide` (calibration frozen → independent DE MAP fits, needed for the multimodal HyperEMG η/τ that gradient-only Adam mis-fits), `global` (per-peptide frozen → Adam on the identifiable shared params), `joint` (refine) — then **promotes a peak-shape hyperprior** (per-parameter Gaussians over the calibrant population's `log σ`/`log τ_r`/`log τ_l`/`logit η`) onto the calibration, which `estimate_n`'s VB path reads via `make_log_prior(shape_centers=…)` to regularize per-peptide shape fits (the principled replacement for a hard `τ`-bound / RT window). Two identifiability fixes are load-bearing: **`d_mz_0` is pinned to 0** (the monoisotopic peak is the m/z reference — a free `d_mz_0` is degenerate with `mz_offset`), and the default `global_params` **excludes the gain** `α(z)`. The gain is identifiable only through the shot-noise (`Var ∝ α²N` vs `Mean ∝ αN`) — and only once the **`log(τ/α)` change-of-variables Jacobian** is in `panel_log_prob` (the data are intensities, scored as the recovered count `N_obs=I·τ/α`; the Jacobian is constant when `α` is frozen but REQUIRED when `α` is co-fit, else the count PMF's preference for smaller counts drives `α↑`/`N→0` without bound). With the Jacobian, co-fitting `α` is well-posed but the second-moment curvature is *weak* (recovery is init-sensitive and partial from a mis-set start) — hence excluded from the default for robustness; calibrate it by adding the gain names (ideally with known-abundance spike-ins). Validated: from calibrants under a perturbed calibration it recovers `mz_offset` (3.0→2.95 ppm), per-peptide `N` (mean +0.1%), and the population shape hyperprior. **ms time base throughout** (`rt`+`τ` in ms, flux [ions/ms], `∫N(t)dt=N_total` with no stray factors); IIT enters the *variance*/accumulated-count `N=I·τ/α` (Eq. 11), not the mean (Eq. 14) — `iit.accumulated_count`. Built on `core.stats` (VI guides + `ParameterTier` from the foundations PR) + `massspec.peptide` envelopes; consumes `XIC_TRACE_TABLE` via the **real-data pivot `observe.observation_from_trace`** (PR-4): packs the long-form trace (one row per observed `(scan, channel)`) + a `SCAN_METADATA`-style table (`scan`/`rt`/`iit`) into the dense `(scan × channel)` `CounterObservation` on a target `Progenitor`'s grid — the inverse of `simulate.observation_to_trace`. ## Code-level invariants (massspec layer)

- **The jar's command line is captured, never transcribed.** Nothing in Constellation should name an EncyclopeDIA program or flag from memory or from an older version's notes. The pinned jar's `-h` output is checked in (`data/_raw/encyclopedia/<version>/help/`), parsed into `data/encyclopedia_cli.json`, and `tests/test_encyclopedia_cli_spec.py` fails if a wrapper emits a flag the jar does not document. This exists because the hand-kept 6.5.15 notes listed `-scribetwodda` / `-scribetwodia` for a jar whose ScribeTwo is `-scribetwo -searchType auto|dia|dda_chimeric|dda`, and nothing noticed. Two caveats the snapshot cannot remove: the help table truncates names at 35 characters (`-numberOfExtraDecoyLibrariesSearche`), and the jar has parameters it does not print (a result library's `metadata` table is the full list) — so "undocumented" is a reason to look, not proof of rejection. The undocumented ones seen so far are kept as a record in `cli_spec.UNDOCUMENTED_PARAMETERS` (where each came from; none tried on the command line); Constellation passes none of them and none is needed for current searches. The jar also contains an `EncyclopediaTwo` class that is in no help text: it is not a working program and is ignored. The install is the whole app directory (the jar needs `lib/` beside it) and runs under its bundled JRE (`ToolSpec.prefer_bundled_jre`; the jar warns outside Java 11–21).
- **A Constellation-written `.dia` is held to the reference writer's output, value for value.** `io.encyclopedia._dia_write` targets what MSRawJava (the library inside EncyclopeDIA 6.x and MSForest) writes from the same `.raw`, and `diff_dia` is the acceptance test: on the lab's Stellar reference set a single-run DIA file matches in every scan scalar, every peak, every isolation window and every shared metadata value, with no tolerance. Getting there took four non-obvious conventions, each of which is one unit in the last place wrong if done the natural way: scalars are stored float32-rounded; `TIC` is the *sequential* float32 sum of the stored intensities (numpy's pairwise sum differs); `ranges.DutyCycle` is computed from the *unrounded* scan times and rounded once; and injection time (float32 ms in a bundle, float32 s in the file) must be divided as the short decimal the float32 stands for (`31.043`), not as the widened float32. The metadata is load-bearing, not decoration — the search reads `rawFileStructure.dataAcquisitionType` / `isStaggered` and `conversion.*` to decide how to treat the run, and copies `sourcename` into every result as `SourceFile` (the key outputs are bound to acquisitions by). Acquisition type is inferred from the data (`massspec.acquisition_structure`: MS2 scans per distinct isolation window, hundreds for DIA and under two for DDA), never asserted by the caller. Two deliberate departures: provenance keys a bundle cannot back (instrument-method text, sample vial) are omitted rather than invented, and for **DDA** runs the `ranges` table lists every distinct window where the reference lists an unrecoverable sample of them. One discrepancy in the reference itself: four of its eight files each lack one MS2 scan that the `.raw` contains and the file's own `acq.ms2_count` counts; Constellation keeps every scan, so its output differs from the reference by exactly those. Because `SpectrumIndex` in a merged file is a running count, `diff_dia` pairs scans by fraction and scan number, not by index. Ion-mobility arrays are refused, not guessed.
- **A search of a Constellation-written `.dia` is held to a search of the reference file, and "the same" means within a repeat search.** Measured 2026-10-11 on the reference wide-window run: `.raw` → bundle → `.dia` → `massspec search` gives exactly the GUI reference's 31,833 precursors and 5,168 proteins, with identical retention times and quantities; for one GPF fraction the Percolator input is row-for-row what the jar computes reading the `.raw` itself. Two searches of one file are not always identical: the scoring is reproducible, but one Percolator feature (`deltaRT`, from the retention-time fit) differs in 40–190 of 76,400 rows between runs, which moves up to about ten precursors across the 1% FDR line. So compare searches with `compare_results` / `massspec encyclopedia compare-results` (overlap and agreement), never by file bytes or by a bare count, and judge a difference against a repeat run.
- **Everything that starts the jar goes through `thirdparty.jvm.run_jar` or `capture_jar`.** EncyclopeDIA 6.x starts a .NET helper server on every invocation (`-h` included) after unpacking its runtime into `java.io.tmpdir`, and does not reliably clean up: every run leaves a directory there (65–80 MB after an error exit) and some error exits leave the server running. Two days of test and survey runs left 1.4 GB in `/tmp` and six orphan processes. Both functions start the JVM in its own session, stop whatever remains of its process group afterwards (also on Ctrl-C, since the JVM no longer gets the terminal's signal directly), and give each run a private temp directory that is removed. A bare `subprocess.run([java, "-jar", ...])` — which three real-jar tests used to do — leaks.
- **The jar's Percolator is a separate executable, and a search is pre-flighted for it.** `-percolatorVersion` picks one of the builds packed in the jar (or, undocumented, the path of any Percolator executable); the jar unpacks it and runs it only after the whole run is scored. The default Linux build (3.01, static, 2017) reads the clock through the legacy vsyscall page, so on a kernel booted with `vsyscall=none` — WSL2 — it segfaults and the jar reports only `Percolator exited with non-zero status: 139`. `search.encyclopedia.percolator.percolator_blocker` detects that combination from `/proc/self/maps` before the JVM starts; `massspec search` refuses with the ways out and `doctor` shows a `percolator` row. New jar-backed commands that end in Percolator call it too. Constellation never patches or substitutes the binary on its own; choosing a different one is the user's `--percolator-version`. The transcriptome pipeline calls the legacy wrapper directly and so has no pre-flight.
- **Batched fragment-ladder construction for bulk readers.** Annotated-spectrum readers (NIST `.msp`, mzSpecLib, search-engine outputs) routinely parse thousands of peptidoforms per file. Calling `fragment_ladder` once per peptide pays per-call torch dispatch + Python-loop overhead `N` times; `fragment_ladders_batch` / `fragment_ladder_indices_batch` group inputs by `(sequence_length, global_isotopes)` and run the inner tensor math once per group. The MSP reader (`massspec.io.msp._read`) chunks entries via `chunk_size=1024`, pre-scans each chunk to discover the minimal `(ion_types, loss_ids, max_charge)` referenced by the chunk's annotations, then issues one batched-index call per chunk. Result: ~40× total speedup vs. naïve per-spectrum dispatch on a 200k-entry library, with bounded memory (each chunk's intermediates are freed before the next chunk starts).
- **An external predictor's m/z is a checksum, never the source of truth.** Koina's intensity models return `mz` alongside `intensities`, and it is tempting to store it directly. Don't: `mz_theoretical` is always derived locally from `massspec.peptide` (`fragment_ladder_indices_batch`), exactly as the MSP reader does, so libraries from different producers stay directly comparable and carry one consistent physics. The returned value is then *compared* against the local ladder and the worst ppm deviation recorded in the run manifest. This is not redundant bookkeeping — it is the only cheap check on modseq translation: if the string we sent described a different molecule than the `Peptidoform` we think we sent (a mis-placed terminal mod, a dropped accession, an off-by-one), the intensities still come back looking plausible while the masses silently disagree. Real-data agreement is ~0.06 ppm, i.e. float32 rounding, so any genuine drift stands far out from the noise. The same rule applies to any future prediction backend.
- **Pre-flight external predictors locally, before the first request.** Model limits (length, charge, supported modifications) are validated against the local overlay in `library.koina.models` and reported with the offending peptide named. Servers reject out-of-range input with opaque errors — Koina's is literally "at least one request failed" — and a multi-million-precursor job that dies forty minutes in on peptide 3.2M with that message is the worst available outcome.
- **Empirical-source libraries may carry partial-ID fragment rows.** `LIBRARY_FRAGMENT_TABLE.ion_type` / `position` / `charge` are nullable because empirical readers (NIST `.msp`, future spectral-library text formats) may encounter peak annotations the project's mzPAF Phase 1 grammar doesn't decode (internal fragments, immonium, unsupported named losses) or annotations that fall outside the biochemistry-licensed fragment ladder (e.g. `y1-H2O` on a fragment with no E/T/D/S residue). Such rows are kept with NULL structured columns + the raw annotation string preserved verbatim so downstream tools can re-parse with future grammar support without re-reading the source. Projections into the strict `FRAGMENT_ION_TABLE` filter on `ion_type IS NOT NULL` first.
- **`intensity_predicted` is float64 and pass-through by default.** Schema dtype is `pa.float64()` (matches mzPeak's choice for intensity arrays — float32 silently quantises Orbitrap/Astral peaks above 2²⁴). Reader defaults pass raw observed intensities through; normalization (max, sum, etc.) is a downstream projection callers opt into. Model-predicted libraries continue to populate normalised intensities; empirical-source libraries (NIST `.msp`, EncyclopeDIA `.elib`) carry raw counts.
- **One EncyclopeDIA result file spells N-terminal modifications two ways, and both must come out as the same peptide.** In 6.9.23, `entries` and `peptidescores` write the modification before the first residue (`[-17.026549]QLSALHR`) and `peptidequants` writes it on the residue (`Q[-17.026549]LSALHR`, or `C[+42.010565][+57.0214635]…` ahead of the residue's own). Two rules follow. (1) The parser resolves a terminal mass against the residue actually at the terminus (`Modification.has_terminal_specificity_for`), not merely "has some N-terminal specificity": −17.026549 is pyro-Glu on Q and ammonia loss on C, and asking the looser question found two candidates and left every pyro-Glu peptide as a bare mass, spelled differently per table. (2) Tables are joined to `entries` through `encyclopedia_residue_form` (leading brackets moved onto the first residue), never by parsing the other table's string, because the residue-attached form cannot say whether an acetyl on a leading K is N-terminal or on the lysine; where two peptides of `entries` share a residue form, the row is counted as ambiguous, not guessed. Before this, 188 pyro-Glu peptides of the first real 6.9.23 result had no peptide-level quantity.
- **EncyclopeDIA modseq parsing at the reader boundary.** EncyclopeDIA's `[+N.NNN]` mass-delta notation is ambiguous between N-terminal α-amine and residue side-chain placement (e.g. `K[+42.011]VERPD` could be K side-chain Acetyl OR N-terminal Acetyl on K — these are chemically distinct molecules). `constellation.massspec.io.encyclopedia.parse_encyclopedia_modseq` resolves this by looking up each mass delta in UNIMOD and applying the modification's `specificities` constraints: terminal-only mods at residue 0 promote to `[Mod]-X` form; mods that fit both placements default to side-chain unless localization evidence overrides. Mass deltas that don't resolve unambiguously pass through as ProForma 2.0 mass-delta `ModRef` entries (no silent misassignment). The function returns a `Peptidoform` directly so callers don't double-parse for downstream fragment annotation; `format_proforma(peptidoform)` populates `PEPTIDE_TABLE.modified_sequence`. The inverse `format_encyclopedia_modseq(peptidoform)` is the writer-side helper — lossy on the chemical-fidelity axis because EncyclopeDIA cannot represent terminal vs side-chain placement (terminal mods collapse onto residue 0). The translation lives in the encyclopedia format adapter at `massspec.io.encyclopedia`, not in `core.chem` and not in `thirdparty/` — it's pure file-format translation, not a tool-jar binding.

## Conventions (massspec layer)

- **"DIA" means the acquisition method, and nothing else, in anything a user sees.** EncyclopeDIA calls its spectra file `.dia`, but that is one tool's internal file format (and it holds DDA runs just as readily), while DIA is a whole family of methods; a command or flag named `dia` reads as "something about data-independent acquisition" to anyone who has not used EncyclopeDIA. So commands, flags and help text call it the **EncyclopeDIA spectra file** and are grouped under the tool: `massspec encyclopedia {export-spectra, import-spectra, compare-spectra}`, `--spectra-file`, `--output-file`. The extension itself is unavoidable (the jar requires it) and is mentioned as an extension. Python names inside `massspec.io.encyclopedia` (`write_dia`, `DiaFile`, ...) keep the literal extension because the module path already says whose format it is. Older surface that predates this rule and still says `dia`: the `process-dia` verb (jar-side conversion, due for removal) and the `--dia` flag on `collision-filter` / `classify-novel-peptides`. Do not add to it. (PI, 2026-10-11.)
- **`Peptidoform.charge` is a serialization artifact, not a chemical property.** The ProForma 2.0 spec encodes precursor charge as a `/N` suffix on the modseq string (and adducts as `/N[+Na+,-H+]`), so a peptidoform parsed from a library record or search-engine output carries the published charge state alongside the residue sequence and modifications. The molecule itself isn't `+2` in solution — that charge state is acquired in the ESI source. `precursor_mz(peptidoform, *, charge=None, ...)` falls back to `peptidoform.charge` when the kwarg is omitted but lets explicit `charge=N` override (e.g. for charge-state grids over a charge-naive peptidoform). If we ever need to separate the format-shaped charge from the molecule-shaped charge, that's a `PrecursorRecord`-style wrapper on top, not a refactor of `Peptidoform`.
- **Spectral libraries split theoretical from empirical.** `massspec.library` carries the protein → peptide → precursor → fragment DAG plus the only true M:N edge (protein ↔ peptide) and entity-level *predicted* properties (RT / CCS / fragment intensity) — sample-agnostic, sequence-derivable. `massspec.quant` carries per-acquisition observations (Protein/Peptide/PrecursorQuant) and *calibrated* per-edge transmission efficiencies (`TransmissionProteinPeptide`, `TransmissionPeptidePrecursor`); `efficiency` is strictly bounded `(0, 1]` on populated rows with `-1.0` as the uncalibrated sentinel. `massspec.search` holds peptide-level + protein-level detection scores (q-values, posterior error probabilities, percolator scores) and is the third sibling — keyed by `(entity_id, acquisition_id, engine)`. Run provenance lives once in `massspec.acquisitions` (`ACQUISITION_TABLE` + `Acquisitions` container + `validate_acquisitions` cross-check); Library, Quant, and Search all reference `acquisition_id`. A higher-level composition layer that unifies Library + Search + Quant per Constellation's "detection-IS-quantification" philosophy is intentionally deferred until a concrete pipeline drives its API. Library/Quant/Search each ship Reader/Writer Protocols + registries with `ParquetDirReader/Writer` as the native lossless form. EncyclopeDIA `.dlib` / `.elib` (the same SQLite container — DLIB and ELIB differ only in which tables are populated) is implemented in `massspec.io.encyclopedia` and self-registers with all three Reader/Writer registries; one shared core produces a `(Library, Quant?, Search?)` tuple via `read_encyclopedia(path)` and slot-specific Protocols (`load_library` / `load_quant` / `load_search`) project out the requested view.
